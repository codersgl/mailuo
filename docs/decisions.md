# 决策记录

记录影响后续实现的决策，只追加。需求与规范见 `docs/intend.md`、`docs/spec.md`，两者由用户维护。

## D1 用 pnpm workspace 管理多应用（2026-09-22）

规范已定下 `apps/web` 与 `apps/api` 两个应用，需要一个工作区把两者的依赖和脚本组织起来。选 pnpm：单一 lockfile、依赖硬链接节省磁盘、`pnpm --filter` 可直接跑单个应用。

`apps/api` 需要准备 better-sqlite3 的原生产物，pnpm 默认拦截依赖的安装脚本，因此在 `pnpm-workspace.yaml` 里用 `allowBuilds` 映射放行 `better-sqlite3` 与 `esbuild`。

注意字段名：pnpm 11 用的是 `allowBuilds`（包名到布尔值的映射）。旧写法 `onlyBuiltDependencies` 会被 pnpm 自动改写进 `allowBuilds`，但值写成占位符 `set this to true or false`，装完依赖仍然不会执行安装脚本。放行后如果依赖已经装好，需要 `pnpm rebuild <包名>` 才会补跑脚本。

## D2 worktree 放在仓库内 `.worktrees/`（2026-09-22）

规范要求通过 worktree 推进、审阅后才合并主干。常见做法是把 worktree 放在仓库同级目录，但当前开发环境只允许写入仓库目录，因此放在 `.worktrees/<分支名>`，并在 `.gitignore` 中排除。

代价：worktree 内要各自 `pnpm install` 一份 `node_modules`。个人项目规模下可接受，换来的是每个 worktree 完全隔离。

## D3 迁移按编号 SQL 文件 + schema_migrations（2026-09-22）

规范要求手写编号 SQL 文件、启动时按序执行、执行记录落在 `schema_migrations`。补充两条实现约定：

- 每个迁移文件在**单个事务**内执行，失败整份回滚且不写入记录，下次启动重试。所以迁移文件内不能自己写 `BEGIN`/`COMMIT`（嵌套事务会直接报错）。
- 文件名必须是 `<数字>_<名字>.sql`。编号重复或缺前缀在启动时报错，避免靠文件名字典序决定执行顺序。

只向前迁移，不实现回滚。个人项目回滚迁移的复杂度高于它的收益，需要回退时直接改数据或删掉 `data/kanban.db` 重来。

已知限制：迁移在启动时执行，没有跨进程互斥。规范确定生产只跑一个进程，所以不做处理；但如果两个进程同时指向同一个不存在的数据库文件，后启动的那个会因「表已存在」而崩溃退出，重启即恢复。将来若真出现多进程启动，把「读取已应用列表 + 执行迁移」整体放进一个 `BEGIN IMMEDIATE` 事务即可。

## D4 数据库 snake_case，API camelCase（2026-09-22）

SQL 列名保持 `parent_id`、`archived_at` 这类写法，与规范里的建表语句一致；HTTP 响应统一转成 `parentId`、`archivedAt`，前端不需要在两种风格间切换。转换只发生在仓储层（`src/repositories/`），路由层直接返回仓储的返回结构。

## D5 完成列 id 固定为 `done`（2026-09-22）

进度计数要判断「子任务是否处于完成列」。规范里三列在迁移中写死，但没有指定 id。约定完成列 id 为 `done`，常量放在 `src/domain/columns.ts`，迁移 001 写入同一 id。改动必须同时改两处。

## D6 读接口的归档过滤参数（2026-09-22，第 4 步实现）

规范的看板查询里有「显示已归档时去掉 `archived_at IS NULL`」这一分支，归档开关属于第一批后半段的功能，所以第 2 步的 `readBoard(db, parentId)` 先固定只返回未归档任务，不提前留参数。

第 4 步做了归档接口，参数按原计划补上：`GET /api/board`、`GET /api/board/:parentId`、`GET /api/tree` 接受 `?includeArchived=1`（也接受 `true`，其它值一律当作关闭），缺省关闭。加在 `GET /api/tree` 上是因为规范要求文件树能「显示已归档」，否则归档后的任务没有任何界面入口可以取消归档。

参数解析：只有 `1` 与 `true` 算开启，其余（`0`、`false`、空串、`TRUE`、`yes`）都当关闭；重复出现时 Hono 取第一次的值。解析集中在 `src/routes/query.ts` 的 `wantsArchived`，读写接口共用。

`GET /api/tree` 的每一项带 `archivedAt`（`null` 表示未归档）。规范第 171 行原本把 tree 的字段写死为四个，前端在「显示已归档」模式下就无法区分归档节点，经用户同意后在规范里补上这个字段。

写接口的响应也读这个参数。原因：前端处于「显示已归档」模式时按 D18 整列替换，如果写响应固定只回未归档任务，改一个标题就会把当前列里的归档卡片抹掉。实测过这条路径（`PATCH /api/tasks/:id?includeArchived=1`），测试钉死。

进度计数口径不随开关变化：`childTotal` / `childDone` 的分母永远是未归档的直接子任务（规范「状态语义」一节），所以带上归档任务时也不会出现归档子任务混进分母的情况。

## D7 删除任务的级联策略：应用层事务递归删除（2026-09-22，第 4 步定案）

规范要求 `DELETE /api/tasks/:id` 级联删除后代及相关依赖记录。`tasks.parent_id` 没有 `ON DELETE CASCADE`，而外键约束已生效，所以直接 `DELETE` 一个有子任务的任务会抛 `FOREIGN KEY constraint failed`。

候选方案：

- 数据库层级联：加一条迁移把 `tasks.parent_id` 与 `task_deps` 的两端都改成 `ON DELETE CASCADE`。SQLite 改不了已有表的约束，必须重建表并搬数据。
- 应用层事务递归删除：一个事务里先递归取子树 id、删依赖、再删任务。

用户拍板选应用层。理由：`task_deps` 要「删除两端任一落在子树里的记录」，这段语义无论如何都得表达一次，放数据库里要靠两条 CASCADE 覆盖，与应用层的删除逻辑分成两处；重建表的迁移对个人项目是没有收益的复杂度。实现细节见 D25。

## D8 未知 parentId 的 404 归路由层（2026-09-22）

`readBoard` 对不存在的 `parentId` 返回该层的空看板，不做存在性校验。规范要求 404，但归属路由层：仓储只负责查询，接入 `GET /api/board/:parentId` 时由路由先查任务是否存在再调用。这条约定写在这里，避免接路由时漏掉。

## D9 后端默认端口由 3000 改为 3001（2026-09-22）

开发机上 3000 常被别的服务占用，启动直接失败。用户确认后把默认端口改为 `3001`，常量在 `apps/api/src/config.ts` 的 `DEFAULT_PORT`，仍可用 `PORT` 覆盖。

这条与规范不一致：`docs/spec.md` 的开发约定写的是「Vite 跑 5173，`server.proxy` 把 `/api` 代理到后端 3000」。规范文件只能由用户修改，待用户同步更新。做前端时 Vite 的代理目标从同一个 `PORT` 变量读取，避免两边漂移。

## D10 新建任务的 orders 取目标列内的 MAX + 1000（2026-09-22）

规范对 `POST /api/tasks` 写的是「在同一父任务下取 `MAX(orders) + 1000`」。同一父任务下可能同时有 `orders = 5000` 的进行中任务和 `orders = 1000` 的待办任务，按整层取 MAX 会让新任务在待办列里拿到 6000。

实现按 `(parent_id, column_id)` 取 MAX，即追加到目标列末尾。理由：`orders` 只用于列内排序（索引 `idx_tasks_board` 也是 `(parent_id, column_id, orders)`），跨列比较没有意义。若规范原意是整层取 MAX，需要用户更新规范并说明用途。

这条 MAX 刻意不排除已归档任务：归档任务将来取消归档时应回到原位，若把它们排除，新任务会插到它们前面。行为由测试固定，避免被「顺手过滤归档」改掉。

## D11 面包屑包含根看板与当前任务（2026-09-22）

`GET /api/breadcrumb/:taskId` 返回 `{ items: [{ id, title }] }`，第一项 `id` 为 `null`、标题固定「根看板」，随后是从根到 `taskId` 自身的每一层。

理由：规范里的例子是 `根看板 / 重构登录 / 前端部分`，最后一段就是当前看板所在的任务，所以接口把当前任务也返回。前端把 `id === null` 的一段链到 `/`、其余链到 `/board/:id`，不需要自己拼前缀。`id` 用 `null` 而不是特殊字符串，避免与真实 UUID 冲突。

## D12 入参用 strictObject，错误体只给第一条（2026-09-22）

- schema 一律 `z.strictObject`，字段名打错时返回 400 而不是被静默丢弃。未知字段的中文文案通过 `strictObject` 的 `error` 回调指定，只替换 `unrecognized_keys` 一种情况，请求体不是对象时仍用 Zod 默认描述。
- 规范要求错误统一为 `{ error: string }`，所以 `validationHook` 只取第一条 issue，压成 `字段名: 说明`（没有字段名时只给说明）。多字段同时出错时只说第一条，不引入 `details` 数组以免偏离契约。

## D13 归档任务下禁止新建子任务（2026-09-22）

`POST /api/tasks` 的 `parentId` 指向已归档任务时返回 400「父任务已归档」，而不是照常创建。归档是整棵子树一起隐藏，在归档任务下建的任务会立刻变成看不见的孤儿；正常界面进不到归档看板，这条只是防御。

## D14 本步的接口边界（2026-09-22）

本步实现：`GET /api/board/:parentId`、`GET /api/tree`、`GET /api/breadcrumb/:taskId`、`POST /api/tasks`、`PATCH /api/tasks/:id`（仅标题、描述、工期）。

未实现、留给下一步：`PATCH /api/tasks/:id` 的移动排序（`columnId` + `position`，要重写目标列 orders）、`PATCH /api/tasks/:id/parent`（要环检测）、`PATCH /api/tasks/:id/archive`（子树归档）、`DELETE /api/tasks/:id`（级联策略见 D7）。移动排序的入参 schema 也还没写，避免留下列表里没有实现的字段。

## D15 错误体统一与写接口的 Content-Type（2026-09-22）

- `onError` 里对 `HTTPException` 做归一化。原因：Hono 在请求体不是合法 JSON 时抛出的是 `HTTPException(400, { message })`，它自带的响应是 `text/plain` 的纯文本，直接放行会违反「错误统一为 `{ error: string }`」的契约。现在只要响应不是 `application/json` 就包成 JSON 错误体，文案也把 Hono 的 `Malformed JSON in request body` 换成中文。
- 写接口（POST/PATCH）要求 `Content-Type` 含 `application/json`，否则返回 400「Content-Type 必须是 application/json」。原因：zValidator 在 Content-Type 不匹配时会跳过解析，请求体变成 `undefined`，报错会变成「列 id 必须是字符串」，而字段其实就在 body 里（`curl -d` 默认发 `application/x-www-form-urlencoded`，很容易踩）。
- `POST /api/tasks` 的校验顺序固定为：字段格式 → `columnId` 存在（400）→ `parentId` 存在（404）→ 父任务未归档（400）。两者同时非法时先报列错误，顺序由测试钉死，调整顺序会改变状态码。

## D16 已归档任务：写接口拒绝，读接口照常（2026-09-22）

写接口一律拒绝归档任务：`POST /api/tasks` 在归档父任务下新建返回 400「父任务已归档」；`PATCH /api/tasks/:id` 与 `PATCH /api/tasks/:id/parent` 对归档任务本身返回 400「任务已归档」。归档语义是「收起来」，允许继续改动它会让归档状态与实际内容脱节，也会让「写接口返回的 `columnTasks` 必然包含 `task`」这条不变量失效（归档任务不在任何列列表里）。要改先取消归档。

读接口不拦截：`GET /api/board/:parentId` 对归档任务返回 200 与空看板。读只做存在性判断，多一个 404 判定只会让「归档任务恢复后再点进去」这类边界多一次失败路径，收益不大。

## D17 成环与父行缺失按脏数据处理（2026-09-22）

`readBreadcrumb` 遇到父子成环抛 `TaskCycleError`（→500 并记日志），遇到父行缺失返回 `undefined`（→404）。这两种情况在外键开启且只走接口的前提下不可达，写出来是为了不在脏数据上返回一条看起来正常但错误的面包屑。测试用直接改库的方式固定这两个行为。

## D18 写接口统一返回 `{ task, columnTasks }`（2026-09-22）

`PATCH /api/tasks/:id` 与 `PATCH /api/tasks/:id/parent` 都返回 `{ task, columnTasks }`：

- `task`：改动后的任务记录（用于字段编辑后刷新卡片）。
- `columnTasks`：该任务所在列的完整有序列表，元素与看板卡片同构（含 `childTotal` / `childDone`）。

理由：规范要求移动后「后端重写目标列内所有任务的 orders 并返回该列任务列表」，前端不做本地重排。字段编辑也返回整列，形状统一，前端拿到响应就能整列替换，不需要为一个接口准备两种解析分支。这是对第 2 步 `PATCH` 返回裸任务对象的改写，没有保留旧形状（个人项目，无外部调用方）。

第 4 步补了一条：`columnTasks` 与请求的 `?includeArchived` 保持一致（见 D6），这样「显示已归档」模式下整列替换不会丢卡片。缺省仍是只含可见任务。

## D19 移动的 position 是目标列里的 0 基下标（2026-09-22）

`PATCH /api/tasks/:id` 的 `{ columnId, position }` 中，`position` 是「任务移出原位置后，插入目标列的下标」，从 0 开始，超出列长度按末尾处理（内部 `Math.min(position, siblings.length)`；schema 已保证非负，所以没有下界处理）。

例：待办列是 `A B C`，把 `C` 移到 `position: 1`，结果是 `A C B`（先移出 C 得到 `A B`，再插到下标 1）。前端从拖拽得到的落点下标可以直接传，不需要自己减一。

重排只在 `(parent_id, column_id)` 范围内发生，只重写未归档任务，编号从 `ORDERS_STEP` 起逐个递增。位置与列都没变的行不写库，避免「拖回原位」把整列的 `updated_at` 全部刷新。

## D20 已归档任务不参与重排（2026-09-22）

移动只重写可见（未归档）任务的 orders，同列里已归档的旁观任务保留原值。它们不参与渲染，重排后可能与可见任务撞号，影响仅限于「取消归档后落点不精确」。另一种做法是把归档任务也纳入编号，但那会让 `position` 的含义（可见列表下标）与内部编号错位，代价更大。行为由测试固定。

被移动的任务本身若是已归档，请求直接被拒（D16），不存在「归档任务被重新编号」的情况。

## D21 改父级：子树跟随，环检测用递归 CTE（2026-09-22）

`PATCH /api/tasks/:id/parent` 入参 `{ parentId, columnId }`（`parentId` 为 `null` 表示移到根看板）：

- 任务挂到新父级下并追加到目标列末尾，`orders` 取新范围内该列的 `MAX + 1000`（取值时排除任务自己，避免同范围移动时多留一个空档）。
- 子树跟着父任务走，不需要额外处理（子任务不参与列渲染）。
- 环检测：用递归 CTE 求任务的子树，判断 `parentId` 是否落在其中（含自身）。CTE 用 `UNION` 而不是 `UNION ALL`，脏数据成环时递归也能终止。命中返回 400「不能把任务挂到自己或自己的后代下」。
- 新父任务不存在返回 404、已归档返回 400、`columnId` 不存在返回 400；同父同级移动等价于「追加到该列末尾」。

## D22 本步的接口边界（2026-09-22）

本步实现：`PATCH /api/tasks/:id` 的移动（`columnId` + `position`，可与字段更新同时提交）与 `PATCH /api/tasks/:id/parent`。

未实现：`PATCH /api/tasks/:id/archive`（子树归档与取消归档的父链恢复）、`DELETE /api/tasks/:id`（级联策略见 D7）。

## D23 写接口的校验顺序统一（2026-09-22）

两条 PATCH 路由统一为：任务存在（404）→ 任务未归档（400）→ 目标列存在（400）→ 父级检查（自环 400 / 父任务不存在 404 / 父任务已归档 400）。

理由：把「目标资源不存在」放在「入参非法」之前更符合直觉，两个接口顺序一致也避免前端为同一类错误准备两套判断。与 D15 里 `POST /api/tasks` 的顺序（先列后父）不同，POST 没有「任务本身」这个主体，先报入参错误更合适。两种顺序都由测试钉死。


## D24 归档：整棵子树一起归档，取消归档恢复父链（2026-09-22）

`PATCH /api/tasks/:id/archive` 入参 `{ archived: boolean }`（必填，没有默认值：省略时无法区分意图）。

- 归档：任务及其全部后代都置 `archived_at`。已经归档的行保留原时间戳，所以重复归档是幂等空操作，也不会白刷 `updated_at`。
- 取消归档：恢复整棵子树，并沿 `parent_id` 向上把仍处于归档状态的祖先一并恢复（规范要求，否则任务会挂在一个不显示的父节点下）。只改 `archived_at IS NOT NULL` 的行，本来就没归档的祖先不会被刷新 `updated_at`。
- 子树与祖先链都用「先读 id，再 `UPDATE ... WHERE id IN (...)`」，不在 `UPDATE` 里内联递归 CTE：那样读源与写目标是同一批行，是否先物化取决于 SQLite 实现。
- 响应是 `{ task, columnTasks }`，与其它写接口同构。归档后任务不在任何列里，所以默认情况下 `columnTasks` 不含它（这是唯一允许「响应的 `task` 不在 `columnTasks` 中」的接口，D18 的不变量在这里失效，前端按「整列替换」处理即可）；取消归档后它回到原列，且因为归档不动 `orders`，位置与原值一致。
- 请求带 `?includeArchived=1` 时 `columnTasks` 含归档任务（D6）：刚归档的任务会作为归档卡片留在列表里，前端不需要为这一个接口特判。归档与取消归档都不重排 `orders`，所以带不带归档，可见任务的相对顺序一致。
- 归档是唯一接受已归档任务的写接口，D16 在这里不适用：它正是把任务放进或取出归档状态的入口。
- 子树归档用一条 `UPDATE` 完成，不逐层递归：SQLite 的递归 CTE 一次取全部 id 更简单。

## D25 删除：先依赖后任务，任务行一条 DELETE 删整棵子树（2026-09-22）

`DELETE /api/tasks/:id` 在 `BEGIN IMMEDIATE` 事务里按三步做：

1. 递归取子树 id（含任务自己）。
2. `DELETE FROM task_deps WHERE predecessor_id IN (...) OR successor_id IN (...)`：一条语句覆盖「任务作为任意一端」的记录，无关依赖不动。
3. `DELETE FROM tasks WHERE id IN (...)`：一条语句删掉整棵子树。

顺序不能反：外键已开启，任务先删会立刻撞上 `task_deps` 的约束。第 3 步之所以能一条语句删掉父子两端，是因为 SQLite 的立即外键约束在**语句结束时**检查，同一语句里删掉父子不构成中间态；这条行为由「四层链」用例钉死，若将来 SQLite 改了语义测试会先失败。

响应是 `{ columnTasks }`（没有 `task` 可回），取删除前记录的父级与列，前端整列替换。删除没有请求体，所以不要求 `Content-Type`。

已归档任务可以删除：归档是「收起来」，删除是清理入口，这是 D16 的第二个例外。

## D31 迁移 runner 支持「重建表」的 no-foreign-keys 标记（2026-09-22）

问题：SQLite 不支持修改已有列的类型或约束，改列名之外的 schema 变化只能重建表（建新表、搬数据、DROP 旧表、改名）。重建过程要 DROP 掉的 `tasks` 被 `task_deps` 和新建的 `tasks_new.parent_id` 引用，而外键开启时 `DROP TABLE` 会先做一次隐式 DELETE，直接撞上约束报错。SQLite 官方建议重建时关闭外键，但 `PRAGMA foreign_keys` 在事务内是空操作，我们的迁移又是「一个文件一个事务」。

方案：迁移文件里用 `-- kanban:no-foreign-keys` 声明，runner 看到标记就

1. 在事务外 `PRAGMA foreign_keys = OFF`；
2. 在事务内执行文件内容，并在提交前跑一次 `PRAGMA foreign_key_check`，发现悬空引用就抛错；
3. 无论成功失败，在 `finally` 里恢复 `PRAGMA foreign_keys = ON`。

校验放在提交前的理由：有悬空引用时整个文件回滚，磁盘上不会留下坏库，`schema_migrations` 也不记录，下次启动可以重试。测试用一份故意删掉父行、留下悬空引用的标记迁移固定这三条行为（抛错、回滚、外键开关恢复）。

标记用整行正则匹配（`^--\s*kanban:no-foreign-keys\s*$`），不是 `includes`：说明性注释里提到这个字符串不该误关外键保护。runner 还会拒绝在有外层事务时运行——那会让 `PRAGMA foreign_keys` 静默失效。

重建表迁移的两条照抄规则（写在 002 的注释里）：重建会连带丢掉旧表上的索引，必须在 RENAME 后手工重建；新表最后必须 RENAME 回原名，否则 `task_deps` 里按名字写的 `REFERENCES tasks(id)` 会静默指错表。

`foreign_key_check` 是全库范围的，因此迁移之前就存在的坏数据（手改库造出的悬空引用）也会拦下这次迁移。这里刻意选择响亮失败而不是跳过：带着悬空引用的库继续跑只会更晚更难查。恢复方式写在报错信息里——按表名与 rowid 修好那些行再重启，迁移已回滚会在下次启动重试。

代价：迁移文件多了一个必须照做的约定；不需要重建表的迁移不要加这个标记——关闭外键期间执行的 SQL 没有外键保护。

## D32 工期最小刻度改成分钟，NULL 表示未估、0 表示瞬时（2026-09-22，用户拍板）

问题：工期原来的单位是「天」且只允许整数。原型里「工期 0.5 天」这种常见的个人任务没法表达；更糟的是 `0` 同时被规范定义为「未估工期」（数据模型一节）和「瞬时」（关键路径一节），两个含义共用一个值，界面无法区分。

决定（用户确认的三条）：

- 最小刻度是分钟，整数存储。CPM 全程按这个整数刻度做加减与比较，不会出现浮点比较松弛时间的问题。
- `NULL` 表示未估工期，`0` 表示瞬时任务，`> 0` 是工期分钟数。三者在界面上必须能分辨。
- 1 天 = 480 分钟（8 小时工作制），只用于展示与输入换算。CPM 不引入工作日、周末或节假日的日历模型——那会把这一步变成另一个量级的工作。

连带改动：

- 字段重命名 `duration` → `duration_minutes`（API 里 `durationMinutes`）。单位换了名字不改，后面每次读代码都要回去查单位；项目没有外部调用方，按规则不留兼容。
- `PATCH /api/tasks/:id` 的 `durationMinutes` 传 `null` 表示改回未估，省略表示不动。`POST /api/tasks` 仍然不接受工期（工期录入属于后续步骤）。
- 迁移 `002_duration_minutes.sql` 重建表：加 `CHECK (duration_minutes IS NULL OR (typeof(duration_minutes) = 'integer' AND duration_minutes >= 0))`（`typeof` 是为了让「整数存储」在数据库层也成立，不只是靠 API 的 Zod），旧的正数乘以 480，旧的 0 与负数一律按「未估」转成 `NULL`（001 没有 CHECK，手改库可能出现负数；历史数据里的 0 只可能是没填）。
- 前端 `formatDuration` 吃分钟数：`null` → 「未估工期」（虚线弱化 chip）、`0` → 「瞬时」、其余折成「N 天 M 小时 K 分」，只保留非零部分。`isDurationEstimated(0)` 为 `true`，因为 0 是一个估过的值。

## D35 写操作后静默重取，不用响应里的 columnTasks（2026-09-22，第 8 步定案）

问题：规范给写接口定的形状是 `{ task, columnTasks }`，前端「整列替换即可」（D18）。真接上写入口时，这条路走不通：

- 新建的响应是任务记录本身，没有 `columnTasks`（`POST /api/tasks` 返回裸任务），新建必须走另一条路。
- 跨列移动会让源列与目标列同时变化，而 `columnTasks` 只给目标列（第 9 步拖拽会撞上）。
- 文件树与面包屑根本不在写响应里；写后不刷新侧栏，树就是旧的（D34 明确留下的那条待办）。

方案：`useAsync` 增加 `refresh()`——**静默重取**：保留当前数据继续显示，拿到新结果后替换。写成功后 `refreshAll()` 一次性静默重取看板、面包屑、文件树。代价是每次写多 3 个 GET（个人应用、本地库，实测几毫秒，肉眼不可见）；收益是前端不需要推算「这次写影响了哪几处」。写响应里的 `columnTasks` 因此不再被消费——后端契约不变，D18 那一半保留但前端不用。

三个细节，都由测试钉住：

- `refresh()` 用一个 ref 标记「这一轮是静默的」，effect 读到后跳过「清空数据」那一步。用 ref 而不是 state：它只影响这一轮 effect 的行为，不该引起额外渲染。
- 静默只对「同一份数据」成立。effect 里用 `previousDeps` 判断 deps 是否变化；若 `refresh()` 与 deps 变化撞在同一轮（写成功的同时切看板），按非静默处理，否则会短暂显示上一层的看板却顶着新地址。
- 静默重取失败时**保留已经显示的数据**（写本身成功了，一次后台 GET 失败不该把可用的界面换成错误页）。这与 `reload()` 的失败语义不同，重试按钮仍然走 `reload()`。

审阅后补的两条：

- 上面那条的代价要写清楚：写成功后若这次后台 GET 失败，界面会停在旧数据上——最明显的是删除成功但列表里那张卡片还在，点它会进 404 看板；恢复方式只有刷新页面或下一次写操作。本地单人部署下这个窗口极短，暂时**接受**并记录，不加提示。将来要补的话，应该在 BoardPage 里给一条非阻断的「刷新失败，点此重试」，而不是把静默失败变回错误页。
- `reload()` 会显式清掉静默标记：否则同一批里先 `refresh()` 再 `reload()`，这一轮会被当成静默，重试按钮点下去看不到加载态。现有 UI 路径不可达（失败态下没有写入口），属于防御。

## D36 「显示已归档」开关上移，看板列也要认它（2026-09-22，第 8 步定案）

问题：第 7 步把这个开关放在 Sidebar 内部，只传给了文件树，看板列固定不含归档任务。加上归档入口后这变成一个死锁——归档一个任务会让它从列里消失，而列永远不显示归档任务，于是「取消归档」在界面上没有任何入口。规范「归档」一节本就写着「已归档任务默认不出现在看板列和文件树中」「侧栏提供一个『显示已归档』总开关」，两处应当一致。

## D37 本步边界与两处对定版原型的偏离（2026-09-22）

本步实现：新建任务（列头「+」→ 列底内联输入行）、卡片右上角编辑热区、右侧 360px 抽屉（改标题 / 描述 / 工期、归档与取消归档、删除带内联二次确认），以及 D35 的写后静默重取。未做，留给后续：拖拽（列内排序与跨列移动、文件树拖动改父级）、深色模式、搜索、依赖与关键路径。

原型文件（`.worktrees/feat-task-crud/prototypes/`）在定版并实现后按前端规则删除，不入版本库。

## D39 条件类不要叠加同一个属性（2026-09-22）

问题：`cx()` 只做字符串拼接、不去重。同一个 CSS 属性写两遍时，谁生效由**生成样式表的源序**决定，跟 class 的书写顺序无关。实例：菜单项写成 `cx(MENU_ITEM, 'text-danger hover:text-danger')`，而 `MENU_ITEM` 里已经有 `text-ink-2 hover:text-ink`；Tailwind 按 theme key 的字母序输出，`.text-danger` 排在 `.text-ink-2` 之前 → 灰色赢。结果卡片菜单里的「删除」在真实浏览器里和「编辑 / 归档」一样灰，而当时的 148 个用例全绿——jsdom 不解析 CSS，这类问题测试挡不住。

这是同一个坑第二次出现：D34 里文件树的选中色 `text-accent` 被归档弱化色 `text-ink-3` 吃掉，当时的绕法是让两组类互斥。

规则：

- 条件类只用来在不同属性之间切换（边框虚实、尺寸、透明度这类）；颜色、字号这类**同一属性的取值**一律拆成互斥的完整类串常量，不要用 `cx` 叠加。`TaskCard.tsx` 的 `MENU_ITEM` / `MENU_ITEM_DANGER` 是示范。
- 判断一个条件类是否真的生效，不能只看 jsdom 用例：要么在真实浏览器里量 `getComputedStyle`，要么把两组类做成互斥后由测试断言「另一组类不在」。

`docs/spec.md` 第 204 行关于卡片编辑入口的描述在本步之后也不再准确（编辑入口现在是「⋯」菜单，抽屉只改字段），待用户更新规范。

## D40 工期上限落到接口层；规范批次顺序对齐（2026-09-22，用户拍板）

**工期上限 9999 天（4799520 分钟），但它不是「修一个 500」——那句话本身是错的。**

第 8 步的审阅报告里写「超出 64 位整数的工期会被 better-sqlite3 绑成 REAL，撞上 `typeof(duration_minutes) = 'integer'` 的 CHECK 变成 500」，D37 照抄了这句。这次真动手前先量了一遍（加上限之前的 main，`PATCH /api/tasks/:id`）：

```
{"durationMinutes": 100000000000000000000} -> 400 {"error":"durationMinutes: 工期必须是整数分钟"}
{"durationMinutes": 9007199254740991}      -> 200，存下来了
```

Zod 的 `.int()` 拒绝的是**不安全整数**，而所有大于 2^53 的值都是不安全整数，于是它们根本到不了数据库，也就没机会被绑成 REAL。那条路不可达。审阅报告在「我没能确认的疑点」里自己写了没跑过 HTTP，是从 SQLite 探针推断的——我不该照抄进 D37。

真正的缺口是第二行：`Number.MAX_SAFE_INTEGER`（约 1.7e10 年）这种「安全但毫无意义」的值会被正常接受并存下来。所以上限做的是**把接口的合法取值域收敛到与界面一致**，`.int()` 那一层继续管不安全整数。测试钉住这个分工：`MAX_DURATION_MINUTES + 1` 与 `Number.MAX_SAFE_INTEGER` → 「工期最多 9999 天」，`1e20` → 「工期必须是整数分钟」。

做法：`apps/api/src/domain/duration.ts` 定义 `MINUTES_PER_DAY` 与 `MAX_DURATION_MINUTES`，`updateTaskSchema` 的 `durationMinutes` 加 `.max(...)`。前端 `apps/web/src/lib/format.ts` 的 `MAX_DURATION_MINUTES` 是同一个数，两处注释互相指向。

**前端那侧挡的不是同一件事**：界面上的上界真正防的是「300 位数字 → `Number()` 得到 `Infinity` → `JSON.stringify` 变 `null` → 静默存成未估工期、还提示已保存」。后端拦不住这个（它收到的是合法的 `null`），所以两处都要有。

**不改数据库 CHECK**：加时间上界要重建表（D31 那套机制），而接口是唯一写入口。规范的数据模型里写明了这层分工：数据库的 CHECK 只保证非负整数，上限由接口拒绝。

**规范批次顺序对齐**：`任务描述编辑面板`（原第二批）与 `工期录入`（原第三批）在第 8 步就已实现，用户确认挪进第一批——第二批只剩「搜索」，第三批只剩「任务依赖（DAG）」与「关键路径计算与可视化」。规范文件平时只能由用户改（见 AGENTS.md），D38 的界面行为那条与这次两处，都是用户明确授权后由我落笔的。

## D41 开发端口改为根目录 .env 单点配置（2026-09-22，用户拍板）

**问题**：开发时端口要同时告诉两个进程——apps/api 监听哪个端口、apps/web 的 Vite 代理转发到哪个端口。D28 的约定是两个命令都带同一个 `PORT` 前缀。

**具体追踪**（2026-09-22 本机）：3000 被 Excalidraw 占，3001 被 VS Code Live Preview 占，3002 被一个只收 WebSocket 升级的服务占（普通 HTTP 请求返回 `426 Upgrade Required`）。用户按启动提示执行 `PORT=3003 pnpm dev:api`，后端正常（`GET /api/health` → 200），但浏览器仍显示 `请求失败（HTTP 404）`：5173 上的 Vite 进程是更早用默认 3001 起的，代理目标在启动加载配置时读一次 `process.env.PORT`，之后不随环境变量变化，于是 `/api/*` 被转给 3001 上的 Live Preview 静态服务，拿回一段 HTML「找不到文件 …/api/health」。前端 `client.ts` 只在响应体是合法 JSON 时取后端的 `error` 文案，HTML 解析失败，回落到 `请求失败（HTTP 404）`，看起来像后端崩了。

**解决方案**：端口写进仓库根目录 `.env`（`.gitignore` 里已忽略），两边读同一个文件——apps/api 在入口调 `loadEnvFileIfPresent()`，`vite.config.ts` 顶部调 `process.loadEnvFile()`。都用 Node 22 自带的 `process.loadEnvFile`，不引入 dotenv。

- 优先级：命令行环境变量 > `.env` > 默认 3001。Node 的 `process.loadEnvFile` 不覆盖已存在的环境变量，所以 `PORT=3003 pnpm dev:api` 仍然优先（有测试钉住）。
- `.env` 不存在时静默跳过（新克隆的仓库没有这个文件）；ENOENT 之外的错误照常抛出。
- 默认值仍是 3001，所以 `docs/spec.md` 里「代理到后端 3001」这句不用改。
- 同一轮把 `server.strictPort` 设为 true：5173 被占用时 Vite 直接失败，不再静默改用 5174，避免「新进程在 5174、浏览器里那个标签还连着 5173 的老进程」。

**为什么不是把默认端口改成 3003**：3003 只是这台机器此刻恰好空着。写死默认值等于把 D9（3000→3001）那次挪端口重演一遍，下次 3003 被占还要再挪，而默认值散在 `apps/api/src/config.ts` 与 `vite.config.ts` 两个文件里，容易再次漂移。

**可选复杂性，这次没做**：不引入 dotenv 之类的依赖，也不做「后端端口被占时自动换端口」——后端自己换了端口而前端不知道，正是这次 404 的成因。

**影响面（审阅后补充）**：

- `apps/api/src/index.ts` 在模块顶层就把 `.env` 灌进 `process.env`，所以生产入口 `pnpm --filter @kanban/api start`（`node dist/index.js`）同样会读到本机残留的根 `.env` 并改变端口。
- 根 `.env` 的键会被 Vite 看见：配置文件先执行（把根 `.env` 写进 `process.env`），Vite 之后才按 `VITE_` 前缀从 `process.env` 取值送给客户端，所以根 `.env` 里的 `VITE_*` 会被内联进前端产物。`PORT` 不受影响。不要往里放敏感值。
- 改 `.env` 不会自动重启：`tsx watch` 不监听 `.env`，Vite 只监听自己 envDir（`apps/web`）下的 `.env*`，两个进程都要手动重启。
- 端口占用时的提示文案同步改了：现在指向「改根目录 `.env` 的 PORT，重启两个进程」，而不是只给 `dev:api` 加前缀——后者会精确复现上面那条 404。

## D42 第 9 步：拖拽改用指针事件自实现，落点实时乐观重排（2026-09-23，用户拍板）

**问题**：第一批只剩拖拽没做。拖拽要解决三件事——列内排序、跨列移动、文件树改父级，规范禁止卡片在列视图里跨层。

**选型**：按前端规则先做了三版可点的原型（原生 HTML5 拖放 / 指针事件 + 克隆卡片 / 显式把手），用户选了**中间那版**。理由：原生拖放的幽灵图由浏览器决定，拖拽期间无法自定样式，也拿不到与真实 DOM 一致的落点预览；显式把手把「拖」和「点」分成两个热区，误触最低但每次拖动多一步瞄准。代价是自己管这些细节：点击与拖拽的区分、滚动时克隆卡片的位置、指针离开列时的取消。

**落点与 position 的换算**（`apps/web/src/domain/board.ts`，纯函数 + 单测）：

- 命中测试在 DOM 上做：`elementFromPoint` 拿到指针压着的元素，`closest('[data-column-id]')` 找到列，再按各卡片矩形中线决定插到哪张之前（没有更靠前的就是列尾）。`data-task-id` 挂在卡片最外层的 `article` 上，卡片菜单也在这个矩形内，所以从「⋯」拖和从卡片主体拖是同一套几何。
- 后半段换算不能省：`position` 的口径是**未归档兄弟里的插入下标**，而列里可能混着不参与重排的归档卡片（D20），于是「渲染顺序里的下标」和它不一样。`positionForDrop` 照渲染顺序数未归档卡片，锚点本身也可能是一张归档卡片（拖到它上方时），这时在未归档子集里找不到它，直接退回列尾会让卡片莫名落到最后一格。
- **换算必须拿「按下时的看板」**：拖拽期间看板是乐观重排后的样子，那张卡片已经在新位置，用它去数卡片会得到另一个下标，差的正是这一次拖动本身。`onStart` 就是在阈值刚过、还没有一次重排时拍快照的钩子。

**乐观重排**：落点在指针移动时就换算成 `{columnId, position}` 并就地重排（`useAsync` 新增 `mutate`），松手时把同一个 position 发给后端。这样卡片不会先弹回原位再跳过去。失败或按 Esc 时整体退回「按下时的看板」。`mutate` 只在已有数据时生效，后续任何一次重取都会用服务端数据覆盖它。

**乐观重排必须复刻后端算法，不能只「插进数组」**。这是审阅抓到的阻断缺陷（两轮各一条，同一来源），追踪如下：

- 后端 `moveTask` 不是把任务插进数组，而是把目标列**未归档**卡片按新顺序重新编号为 1000、2000、……，归档卡片保留自己的 orders，最后按 orders 排序。
- 第一版前端只把卡片插进数组、把归档卡片钉在原地，于是「显示已归档」打开时预览与落库结果会分叉，松手后卡片跳到别处。
- 改成重新编号后仍有第二个分叉：后端对「新编号 == 原 orders」的任务**不写**（`previous.orders === orders` 早退）。不加这条，归档卡片会被挪动。例：未归档 `[B@1000, A@2000, C@3000]` 加归档 `X@9000`，把 C 留在列尾时谁都不该被重写，X 仍在最后；一律重写则 C 变 2000、A 变 1000，`X@9000` 反而被挤到前面。
- 归档与未归档卡片 orders 撞值时的平局次序，后端那条 `ORDER BY t.column_id, t.orders` 没有次级键，实际取扫描顺序（rowid 升序 = 插入顺序）。前端用 `createdAt` 升序对齐（`compareOrders`）。这是「尽量一致」，真出现 createdAt 也相同的数据时以后端为准，下一次重取会纠正。
- 已知的模型限制：position 只定义在未归档卡片上，所以**渲染在列尾的归档卡片无法被越过**（列尾落点只能落到未归档序列末尾）。要根治得让归档卡片也参与编号，属于后端模型变更，本次不做，留在 D20 的口径里。

**让位动画（用户验收后又改了一次）**：卡片位置变了就做 FLIP 动画，**只在拖拽期间**开。平时新建、归档、换看板也会改卡片位置，那些场合加动画只会显得飘（D35 的静默重取会重画整块看板，加了动画就是一片乱动）。`board` 必须在依赖数组里（少了它，`enabled` 一个拖拽里只从 false 变到 true 一次，effect 不会再跑——审阅发现的）。

用户验收时报告「拖动时其他卡片短暂消失」，实测复现出来的是这个动画的缺陷，追踪如下：

- 触发：在第二、三列之间快速来回拖动（每次指针移动只隔 10ms，同一张卡片会在上一段动画没跑完时就开始下一段）。
- 现象：同一列里其它卡片的相对位置**每帧翻倍**——622px → -665 → 1552 → -2168 → 3985 → 10353，卡片被 `translate` 到视口外（视口高 761，卡片挂在 y=1742 甚至更远），肉眼就是「卡片消失」。A/B 实测：关掉动画 0 次异常，打开 98 次。
- 原因：第一版用「写 `transform` + 下一轮渲染再放开 `transition`」的 CSS 过渡写法。这种写法必须在**同一帧**里写起点，而起点是从 DOM 量出来的；重入时量到的是**动画中途的位置**，误差于是逐帧累积。我一开始还量错了对象——`getBoundingClientRect` 当时返回的是被 transform 平移过的位置，等于把动画的输出又喂回输入。
- 方案：改用 Web Animations API（`card.animate([...], { duration })`）。它自带起点/终点、可以被 `cancel()`，重入前先 `cancel()` 掉旧动画再量布局位置，动画从「当前看到的位置」继续，误差不累积。顺带删掉了「先写 inline style 再清掉」那套容易自相矛盾的顺序处理。
- 交叉验证：同一段代码在慢速同列排序时动画照常执行（实测同时最多 2 个动画在跑、24 个采样点），快速来回时 0 次异常；把实现换回 CSS 过渡那版，同一个脚本立刻报 98 次异常。
- 回归测试：`useCardFlip.test.tsx` 用假 rect 与假 `animate` 钉住三条不变量——量位置前先 `getAnimations().cancel()`、位置没变不做动画、换过列的卡片不做动画。jsdom 没有真实 Web Animations API，所以它测的是「调用了什么、按什么顺序」，真实手感仍由浏览器验收。

另外把换列的卡片排除在动画之外：跨列时 React 把节点搬到另一列的 DOM 里，两边布局位置可能相差上千像素，补一段横跨两列的动画既难看也没意义。

**顺带改的一处布局**：看板网格的 `items-start` 让每列只有内容高，于是「拖到本列末尾」没有落点——最后一张卡片下面就是网格空白，指针不在任何一列里。列改成 `self-stretch` 撑满网格行高，列尾空白才成为可用落点。这条是浏览器验收时抓到的：jsdom 用例量不到几何。

**文件树拖动**：与卡片共用同一套指针语义，但不克隆卡片（树里那一行本来就在，克隆反而看不清落点），只是被拖的行降透明度、候补父级整行高亮 + 2px 强调色左竖条。落点分两段：悬停行上半区 = 成为它的子节点，下半区 = **与它同级、排在它后面**（目标本身是顶层节点时新父级就是 null，也就是回到根层）——早期版本让顶层节点的下半区退化成「成为它的子节点」，于是「拖到 A 下面」会变成「拖进 A 里面」，与画出来的插入线不是一回事，被 `useTreeDrag.test.tsx` 抓到。拖到自己或自己的后代下不显示任何落点、松手也不生效——后端另有 400 环检测兜底。落库时把任务**当前所在列**带过去，后端只会把它追加到那一列末尾，所以这一步只换层级、不换列（界面上画的「排在 X 后面」只是提示，树不支持排序）。成功后只重取树：改父级不影响当前看板的卡片与面包屑。

**点击与拖拽的分界**：阈值 4px，之内的位移仍是一次点击（进入子看板）。超过阈值后浏览器仍会在 `pointerup` 后补一个 `click`，必须吞掉，否则拖完一张卡片会顺手进入它的看板。

这里记录一条**被实测推翻的推断**：第一版写的是「`pointerup` 与 `click` 在同一条任务链上，`queueMicrotask` 一定晚于 click」，因此用微任务清抑制标记。审阅者用 headless Chrome + CDP 派发真实鼠标事件测得顺序是 `pointerdown → pointermove → pointerup → 微任务 → click`——微任务比 click 还早，标记在 click 到来前就被清掉，抑制完全失效；只在小幅拖动（松手点仍在同一张卡片上）时才会露出，跨列拖动常常因为 click 被派发到公共祖先而侥幸没事。现在改成**按时间窗口**：拖拽结束后的 300ms 内的 click 算尾巴，`begin()` 会把窗口清零，所以下一次按下之后的点击永远不受影响（这个窗口期由单测钉住）。同一个坑在真实浏览器里复核过一次，不再靠推理。

**指针被浏览器接管（`pointercancel`）按取消处理**，不把落点提交出去；两个 hook 在卸载时也走 `onCancel`（否则拖到一半换看板会静默丢掉这次拖动）。

**可选复杂性，这次没做**：贴近视口边缘的自动滚动、键盘可达的拖拽、拖动时自动展开折叠的父节点、克隆卡片跟随卡片高度变化（拖拽期间卡片不会变高）。个人使用下先接受。

**验收方式**：jsdom 测不了指针拖拽（没有布局、`elementFromPoint` 是 undefined），所以用 headless Chrome + CDP 派发真实鼠标事件跑了一遍：跨列插到锚点前、同列排序、列尾空白落点、列外松手撤销、阈值内仍是点击、树改父级与拒绝拖到后代，DOM 与后端落库都对上。这类脚本不入库，验收完即删。

入库的那一层是「能用假几何在 jsdom 里测的部分」：`board.test.ts`（含归档混排的三种布局，对照后端实测输出）、`tree.test.ts` 的 `resolveTreeDrop`/`descendantIds`、`useAsync` 的 `mutate`、`useCardDrag.test.tsx`/`useTreeDrag.test.tsx`（阈值、落点去重、Esc、pointercancel、点击抑制——**测试里必须先 `await act(async () => {})` 再派发 click**，否则微任务被挤到 click 之后，错误的微任务实现也能通过，这是审阅指出的假通过用例）。

**审阅补出的一条竞态**：写成功后的静默重取若在拖拽中途返回，会把卡片打回拖拽前的顺序。`refreshAll` 因此在「指针按在卡片上」期间跳过看板重取（树与面包屑照常），松手后本来就会再取一次。标记由 `begin` 返回 true 时置位，并用一条「当前没有拖拽在跑」的 effect 兜底清零——否则 `pointerup` 没派发到 document（指针在窗口外松开）时标记会永久卡住，之后所有写操作都不再看板刷新。

**「这一层还是按下时那一层吗」不能比较看板对象身份**：乐观重排每改一次就生成一个新看板对象，所以拿对象身份做守卫会在第一次落点变化之后把所有后续预览和落点提交全部挡掉——卡片看起来能拖、插入线也在，松手却什么都不发生（写请求一个都没有）。这是浏览器端到端验收抓到的：jsdom 用例与单测都用假几何，走不到「第一次重排之后」的路径。守卫改成比较 `parentId`（按下时记下，预览/落点/取消时比对），层真的被换掉（点面包屑、后退、切「显示已归档」）时才放弃这次拖拽。

**worktree 环境注意**：本机沙箱里 pnpm 默认 store（HOME 下）不可写，`pnpm install` 会以 `ERR_SQLITE_ERROR: unable to open database file` 失败；在 worktree 里用 `pnpm install --store-dir <仓库内的路径>` 即可，对应目录加进 `.gitignore`。与代码无关，只是这台机器的沙箱限制。

## D43 第 10 步：深色模式靠覆盖令牌实现，顶栏放三态控件（2026-09-23，用户拍板）

**问题**：第一批只剩深色模式。`docs/spec.md` 的「主题」只规定了机制——Tailwind 用 class 策略在 `html` 上切换 `dark` 类、偏好存 localStorage、首次访问跟随 `prefers-color-scheme`、手动切换后以本地偏好为准——配色本身要另选，而且它是全屏观感，必须让用户看着挑。

**配色选型**：按前端规则先让子代理做了三版单文件可点原型（各自能实时深浅切换，并附一张 WCAG 对比度表）：A「忠实反相」把浅色的明度关系整体翻转、色相照旧；B「近黑高对比」画布近黑、层次靠表面亮度阶梯而不是边框；C「冷灰蓝 + 强调色随主题换色」。用户选 **A**，控件选 **三态**。

**核心实现决定：组件类名一个都不改，靠 `.dark` 覆盖同名令牌。** 现在所有颜色都走 `@theme` 里的语义令牌（`bg-surface`、`text-ink-2`、`border-line-strong`…），所以深色只需要在 `.dark` 里重新声明 `--color-*`。Tailwind 对颜色生成的是 `var(--color-surface)` 这种运行时引用，实测深色下 `body` 背景是 `rgb(23,25,29)`（= `#17191d`）。替代方案是给每个组件加 `dark:` 前缀，那等于把「配色」这件事重新散回三十来处类名里，以后换配色要全文搜——这正是当初把颜色收进 `@theme`（D29）要避免的。

`.dark` 覆盖块**故意不加 `@layer`**：Tailwind 把 `@theme` 产出的 `:root{--color-*}` 放进 `theme` 层，层外规则无条件排在层内规则之后，所以既不需要 `!important` 也不靠选择器权重取胜。

规范说的 `darkMode: 'class'` 在 Tailwind v4 里没有这个配置项，等价物是 `@custom-variant dark (&:where(.dark, .dark *))`，已加上。当前没有任何 `dark:` 工具类用到它，但保留的理由不是「规范点名」而是：删掉它，`dark:` 会静默退回 Tailwind 默认的 `@media (prefers-color-scheme: dark)`。而这个界面允许用户手动覆盖系统偏好——用户在深色系统下选了浅色，某个组件却仍按系统变深，是最坏的一种错。留着它，这类写法根本写不出来。

**阴影不能放 `@theme`（实测踩到的坑）**：三处阴影原先写死在组件里（`shadow-[0_6px_16px_rgba(29,33,38,0.12)]` 之类），深色下必须换更重的纯黑，否则「拖拽克隆卡」会在深色画布上顶出一圈比背景还亮的灰边。第一版把三个 `--shadow-*` 放进 `@theme`、在 `.dark` 里覆盖，看起来和颜色一个套路，但实测深色下 `.shadow-menu` 算出来仍是浅色那串 `rgba(29,33,38,0.12)`。原因：Tailwind 会把 `--shadow-*` 的**值**在构建时内联进 `.shadow-*` 工具类，而 `--color-*` 生成的是 `var(--color-*)`——前者只认构建时那一份，后者运行时会跟着主题变。所以阴影改成「`:root` / `.dark` 里普普通通的自定义属性 + `@utility shadow-menu/shadow-panel/shadow-ghost` 读 `var(...)`」，产物是 `.shadow-menu{box-shadow:var(--shadow-menu)}`。这个坑不实测很难发现：类型检查、单测、构建都不会报。

**首屏定色必须内联在 `index.html`**：放到 React 里定色不够——模块要等 bundle 下载并执行，中间浏览器已经按浅色画过一帧，深色用户每次刷新都会先白一下。所以 `index.html` 的 `<head>` 里多了一段纯字符串脚本，在样式生效前读 localStorage / `matchMedia` 并把 `dark` 类挂上。代价是这段逻辑与 `src/lib/theme.ts` 重复了一份；重复是这一步唯一不能省的地方（内联脚本不能 import 模块），所以用 `test/themeBoot.test.ts` 把脚本从 `index.html` 里抽出来**真的执行一遍**来防漂移：用 `THEME_KEY` 写入、断言 `html` 上的类，key 或取值格式一变就红。验证防闪烁本身用的是 CDP：`Page.addScriptToEvaluateOnNewDocument` 里记下第一个 `requestAnimationFrame` 时 `html` 上有什么类，深色系统下拿到的是 `dark`，也就是首帧画出来就是深的。

**三态的语义（`hooks/useTheme.ts`）**：`choice` 是用户选过的偏好，`null` 表示「跟随系统」；`theme = choice ?? system`。刻意不用 `usePersistentState`：那个 hook 挂载时就把初始值写回 localStorage，「没选过」这个状态于是永远消失，首次跟随系统只在第一次访问那一次成立。现在只在用户真的点过之后才写；点「跟随系统」是**删掉**这个键（`storage.ts` 新增 `removeStored`），而不是存一个字面量 `null`——后者会在 localStorage 里留一条 `"null"`，以后排查时看不出是「清空」还是「写坏了」。跟随系统期间还挂着 `matchMedia` 的 change 监听，用户在系统设置里切深浅时页面不刷新就跟着变；一旦选过就拆掉监听。单测把这几条都钉住了，其中「监听器数量」是「还在不在跟随」最直接的证据。

**`text-white` 改成 `text-on-fill`（新增令牌）**：三个方案的对比度表都指向同一件事——`accent` 在深色下必须提亮才能当文字色用，可一提亮，`bg-accent` 上的白字就只剩 2.6–2.9:1。所以「填充色」和「填充色上的文字」拆成两个令牌：`--color-on-fill` 浅色是 `#ffffff`（和原来一模一样），深色是 `#17191d`。同样受影响的还有确认删除按钮（`bg-danger`）。一个令牌同时服务 accent 与 danger 两种填充，是刻意的：浅色两者都是白字、深色两者都用近黑，现在没有需要分开的证据，真需要时再拆。

**这四处硬编码也一起收了**：`--color-scrim`（抽屉遮罩）、`--shadow-menu`、`--shadow-panel`、`--shadow-ghost`。深色下遮罩必须换纯黑（半透明深灰蓝会把画布「提亮」），实测深色下 `bg-scrim` 是 `rgba(0,0,0,0.5)`。

**浅色侧没有动**：把 worktree（5174）与主干（5173）的同一批元素计算样式逐项对比，`body` 背景/字色、顶栏背景、卡片背景/边框、列标题字色全部一字不差，唯一不同的项是主干上不存在的主题控件本身（`#eef2fc` / `#4c6fce`，正是浅色的 accent-weak / accent）。截图对比也在同一轮做过。

**已知不达标项，保持定版原值**：深色 `ink-3/surface` 是 4.17:1，低于 4.5（用于 11px 的弱提示文字）。浅色现版这一项是 2.98，所以深色是变好而不是变差；提到 4.77 要牺牲它与 `ink-2` 的层次差，属于配色改动而非本次范围，留待用户决定。

**可选复杂性，这次没做**：给深色单独一套强调色（原型 C 的方向，代价是深浅两套品牌色）；按时间自动切换；`color-scheme` 之外的滚动条样式定制；认不出的地址那一页没有顶栏、因而没有主题控件（主题本身照常生效，`html` 上的类由内联脚本决定）。

**验收方式**：jsdom 没有 `matchMedia`（实测 `typeof window.matchMedia === 'undefined'`），所以 `systemTheme()` 与监听都做了兜底、按浅色算；测试里用 `test/mediaStub.ts` 装一个可控的 `matchMedia`。真实浏览器行为用 headless Chrome + CDP 复核：浅色/深色/点按钮/刷新保持/交还系统五步的 `html` 类与计算颜色、首帧类、以及运行中切系统偏好；另外在深色下真的拖了一次卡片，确认克隆卡的阴影立得起来、插入线是 `rgb(123,149,232)`。这类脚本不入库，验收完即删（`prototypes/`）。

**审阅发现（两条，都已修）**：

- **交还给系统时用了过期的系统偏好**。追踪：`useTheme` 里 `system` 是一份 state，只在「跟随系统」期间挂 `matchMedia` 监听更新。系统深色 → 用户选浅色（监听被拆掉）→ 期间系统变成浅色（没有任何人在听，state 停在 `dark`）→ 用户点「跟随系统」，此时 `theme = choice ?? system` 取到的是那份陈旧的 `dark`，页面跳回深色，而系统明明是浅色。修法：`choose(null)` 时顺手 `setSystem(systemTheme())` 重读一次当前系统偏好。这条是审阅者用探针用例挖出来的，已收进 `useTheme.test.ts`（「不跟随期间系统变过，交还时按现在的系统来」）。它只在「不跟随期间系统恰好变过」时才现形，手工点很少碰到。
- **缺一条守着核心设计的测试**。整个方案依赖「`@theme` 里的令牌在 `.dark` 里都有覆盖」，而漏一个的后果是静默的：该令牌在深色下保持浅色值，类型检查、其它单测、构建全都不报——阴影那次就是这么踩到的。新增 `themeTokens.test.ts` 直接读 `index.css`，断言两套 `--color-*` 集合相等、两套 `--shadow-*` 集合相等、且每个阴影令牌都有同名 `@utility` 在读它。并做了变异检验：删掉 `.dark` 里的一行令牌，这条测试立刻红。

**审阅提出的其余调整（都采纳）**：`useTheme` 不再返回 `theme`（没有消费者，是死 API，生效与否由 html 上的类体现）；主题按钮补上与卡片「⋯」、列头「+」相同的 `focus-visible` 聚焦环（原先用的是 UA 默认环，同一个顶栏里两种焦点样式）；`themeBoot.test.ts` 定位内联脚本的正则从「第一个 `<script>`」改成必须命中 `prefers-color-scheme`，并补了「存了认不出的值 → 跟随系统」这条只有内联脚本才有的分支；三个 `@utility` 挪到 `.dark` 之后，紧挨着它们读的那两组变量。

**这次改动自己踩到的第二个坑（浏览器验收抓到的）**：把 `@utility` 往下挪的同时，我把浅色阴影的 `:root` 也挪到了 `.dark` **之后**，深色阴影当场失效——`--color-*` 在 `layer theme` 里，层外的 `.dark` 无条件赢过它，所以顺序随便；但 `--shadow-*` 浅色那份是**未分层的 `:root`**，与 `.dark` 权重同为 (0,1,0)，于是后写的浅色赢了。现象是深色下菜单阴影仍取 `rgba(29,33,38,0.12)`，而 `themeTokens.test.ts` 只比对「两套令牌名字成对」，完全测不出来（它守的是漏写，不是解析顺序）。修法是把浅色 `:root` 放回 `.dark` 之前，并补一条断言把这个顺序钉住（`indexOf('--shadow-menu') < indexOf('.dark {')`）。教训写在这里：令牌成对 ≠ 生效，涉及未分层规则的顺序必须实测。

**阴影工具类展开写 `box-shadow` 的原因**：审阅指出第一版 `@utility shadow-menu { box-shadow: var(--shadow-menu) }` 丢掉了与 `ring-*` 的组合能力（Tailwind 内置 `shadow-*` 是往 `--tw-shadow` 写值，再由一串 `var(--tw-inset-shadow), …var(--tw-ring-shadow), var(--tw-shadow)` 拼成最终值，所以环和阴影能共存；整体赋值会把环吃掉）。今天没有任何元素同时用阴影和环，但既然要自定义工具类，就让它和内置 `shadow-*` 行为一致。已实测：同一个元素上 `ring-1 ring-accent shadow-menu` 的环与阴影都在。

**`--color-scrim` 的深色值没有原型依据**：定版原型 A 为了让用户看清配色，去掉了抽屉遮罩，因此没有这个令牌；我按「深色遮罩用纯黑并加重」的常规取了 `rgba(0,0,0,0.5)`（浅色仍是原来的 0.28）。这是本次的判断，不是原型 A 的值，需要调整直接改这一个数。

**审阅认为可以不动的地方（同意，记录在此免得下次重开）**：三态控件继续用 `role="group"` + 三个 `aria-pressed` 按钮（省掉方向键处理，代价是读屏逐个报「切换按钮」）；`--color-on-fill` 一个令牌服务 `bg-accent` 与 `bg-danger`（浅色都配白、深色都配近黑，没有需要分开的证据）；`removeStored` 保留（写 `null` 会在 localStorage 留一条读不出意图的记录）；`mediaStub.ts` 放在 `test/` 下不叫 `.test.ts`（vitest 默认只收 `*.test.*`，typecheck 照样管）；`TopBar.test.tsx` 里用 `within(面包屑)` 收窄断言而不是排除法。

## D44 测试不要断言还没落盘的副作用（2026-09-23）

**问题**：深色模式合并进主干后，全量测试在**两套并行跑**（相当于 CI，或本机同时开两个套件）时偶发失败，约十次里错两次；串行跑从不失败，所以之前一直没露头。

**追踪**：失败的是 `Sidebar.test.tsx` 的「当前看板的祖先被折叠过时自动展开」，错在最后一行——`expected '["a","b"]' to be '["b"]'`。界面已经展开了祖先（上一行 `findByText('补单元测试')` 通过），但 localStorage 里还是旧值。原因是展开走 `setCollapsedIds`，**落盘却在 `usePersistentState` 的 effect 里**，即那次渲染提交之后；`findBy*` 只等到 DOM 出现，不保证 effect 已经跑完。机器越忙，那一帧越容易输掉。

**对照实验**（避免误判成「深色模式改坏了 Sidebar」）：合并前的 `adfe4cb` 单独建 worktree，同样两套并行跑 5 轮共 10 次，全绿；主干同样跑法 5 轮里红 2 次。结论：既有竞态，被新增测试带来的负载暴露——这一步把 web 测试从 20 个文件 / 197 项加到 25 个 / 226 项，worker 争用变高。

**修法**：那一行改成 `await waitFor(() => expect(...).toBe(...))`。改完同样两套并行跑 10 轮共 20 次，全绿。

**顺带检查过的同类写法**（都安全，没动）：`fireEvent.click` 之后的断言（`act` 会把 effect 冲干净，见 `Sidebar.test.tsx:108` 与 `App.test.tsx:503`）；`usePersistentState.test.ts` / `useTheme.test.ts` 里在 `renderHook` / `act` 之后的断言。另外 `useTheme.choose()` 把写盘放在事件处理函数里而不是 effect 里，天然没有这个竞态——D43 当时只是为了「没选过就不写」，顺带也躲开了这一类。

**规矩**：要断言 localStorage 或任何 effect 的产物时，要么紧跟 `fireEvent` / `act`，要么用 `waitFor`；只靠 `findBy*` 等 DOM 不够。判断一条 flaky 测试归谁时，先在改动前的提交上做同样的并行对照，别凭「看起来无关」下结论。




## D45 第 11 步：搜索在主区整块呈现，匹配只做连续子串（2026-09-23，用户拍板）

**问题**：第一批做完后第二轮只剩「搜索」，而 `docs/spec.md` 里第二批只有一行「搜索。」——界面形态、匹配口径、结果长什么样都得定。

**原型选型**：按前端规则先做三版可点原型（单文件 HTML，用真实令牌，可切深浅），各自附「取舍说明」：

- A 顶栏搜索框 + 输入即出的下拉面板（460px 宽、最多 8 行）；
- B 侧栏顶部搜索框 + 结果就地替换文件树；
- C 顶栏搜索框 + 主区整块切成结果页，按列分组。

用户选 **C**。这一步的界面因此照 C 实现：结果页头一行是「找到 N 个任务」+ 搜索词回显 + 「返回看板」，下面按列的固定顺序分组（空组不出现），每行是标题（命中片段高亮）+ 层级路径 + 工期胶囊（未估就不画），归档结果带「已归档」标记。

**匹配口径：只做连续子串，不切词、不做顺序模糊匹配。** 原型 C 的演示版做了更强的匹配（连续子串优先、退化为按序跳字、多词需全中、四档相关度排序），实现时**刻意没做**：那要把打分搬进 SQL（或取回候选后在 JS 里算），摘要与高亮也要支持非连续命中，是另一个功能量级，而规范对这一批只写了「搜索。」。代价很具体：搜「前部」搜不到「前端部分」。要加属于下一步。

落地的口径：

- `GET /api/search?q=…&includeArchived=1`，匹配 `title` 与 `description`，大小写对 ASCII 不敏感（SQLite `LIKE` 默认行为），`%`、`_`、`\` 按字面转义（`toLikePattern` + SQL 里的 `ESCAPE '\'`）。
- 排序：「标题命中的排前面」+「最近更新的排前面」+ `id`。不做相关度打分——个人规模下标题命中与否已是用户能理解的最强信号，再加一套评分只会让人猜不透顺序。
- 上限 50 条，多取一条判断 `truncated`，界面提示「找到 N 条以上任务」。
- 每条结果带 `path`（祖先链，复用 `readBreadcrumb` 去掉自己那一项）与 `snippet`（命中在描述里时，以关键词为中心、换行压成空格、两端按需加省略号）。摘要与高亮都按同一个口径折叠空白与大小写，否则会出现「SQL 命中、界面却完全没有高亮」。
- 响应还带 `columns`（列 id、列名、顺序）。这是给「按列分组」用的：搜索是全库的，不该因为当前这一层看板取不到（被别处删掉、请求失败）就画不出来。
- 都是读接口该有的形状：`includeArchived` 沿用 `wantsArchived` 的统一判定；多余的查询参数一律忽略（`z.object` 而不是 `z.strictObject`，与 `/api/board` 等一致）。

**前端：不复用 `useAsync`，另写 `useSearch`。** `useAsync` 是「取一份数据、三种状态、过期响应丢弃」，而搜索要表达两件它表达不了的事：关键词为空时**不发请求**（`idle`），以及打字期间**保留上一批结果**而不是退回 loading（本机请求只要几毫秒，退回 loading 只会让列表每停顿一下就闪一次）。代价是两套状态机并存，所以记在这里，免得后来者以为漏看了 `useAsync`。

其余前端口径：

- 200ms 防抖，输入停顿才发请求。
- `ready` 状态里必须记住**这批结果属于哪一次搜索**（关键词 + 「显示已归档」开关）。回调一到就把结果写进 state，而输入框与开关可能已经又变了；界面用它来高亮、写空状态文案，`BoardPage` 用它判断 Enter 该不该动作。少了关键词，防抖窗口内按 Enter 会打开上一个关键词的结果，旧结果还会被新词重新高亮成「标黄的词并不匹配这一行」；少了开关，切开关后的 200ms 里空状态会按新开关说话（说「打开显示已归档试试」而开关已经开了）。
- 键盘 ↑↓/Enter/Esc 只在搜索框的 `onKeyDown` 上处理（焦点打字时一直在那里），输入法组合期间（`nativeEvent.isComposing`）一律不接管：组合期间方向键在给候选词用、Enter 是确认选字。提示文案因此写明「在搜索框里」。
- 进入任务（Enter 或点行）顺手清掉搜索词：留着的话结果页会盖住刚打开的那一层，看起来像「点了没反应」。
- `maxLength` 用与后端同一个 100（`domain/search.ts` 的 `MAX_QUERY_LENGTH`），敲不进去比让后端回一条「q: 搜索词最多 100 字」友好。分工与工期上限一样（D40）。
- 搜索态下写操作也会重取搜索：文件树拖动会改结果的层级路径，归档会改「已归档」标记。这种情况下唯一的写入口就是文件树，看板本身被结果页盖着。
- 搜索框宽度 240px，但可以被压到 110px。窄屏（375px）下品牌 + 搜索框 + 主题控件三样放不下，固定宽度会把主题控件顶出视口（真机实测 `header.scrollWidth` 491 > 375）。

**已知限制（都是刻意的，不是漏做）**：

- 浅色下未选中行的命中底色 `accent-weak` 对白底只有约 1.12:1，高亮主要靠字重（选中行更明显：底 `accent-weak` + 左竖条 + 命中底 `accent-border`）。两个值都是定版原型 C 的原样，没有实现偏差；要更明显就得动配色，留给用户决定。
- 键盘选中态对读屏不可见（没有 `listbox`/`option` + `aria-activedescendant` 那套语义），只有视觉。结果行的无障碍名字直接由可见文本组成（不设 `aria-label`——它的优先级高于内容，会把摘要、路径、工期、「已归档」一起挤出名字）。
- 结果不落库、不记搜索历史、不做分页；关键词不切词、不支持拼音。

**验证方式**：单测 434 项（api 143 / web 291）+ 两端类型检查 + 生产构建。jsdom 测不了真布局与真事件，所以在真实 Vite + 真实 API + 用户真实库副本上用 headless Chrome + CDP 跑了 21 项验收（脚本不入库，放在 `.tmp-verify/`，验收完删掉）：输入即出结果页、按列分组、路径与工期、归档任务带标记、深色切换、Esc 返回、↑↓/Enter 进入正确的那一条、描述命中补摘要、点行进入、空状态两种文案、**防抖窗口内 Enter 不动作**、**结果跟上后 Enter 才进入**、375px 窄屏顶栏不溢出、页面无未捕获异常。

**审阅发现（两轮，都已修）**：

第一轮抓到的阻断缺陷是防抖窗口内按 Enter 打开上一个关键词的结果（追踪：搜「甲」→ 改成「乙」→ 200ms 内按 Enter → 实测进了 `/board/甲`）。同一根因还有三个症状：旧结果被新词重新高亮、计数与输入框不一致、旧结果为空时对还没搜过的词直接显示「没有匹配」。修法就是 `ready.keyword` 那一条。这条只有真机/真计时才容易撞上，单测里必须先构造「结果已到手、输入框又变了、请求还没回来」这个中间态。

**第二轮复核（对着修复再查一遍）**：

**树保持挂载、用 `hidden` 藏起来，不卸载。** 第一版写的是 `{!collapsed && <div>…</div>}`，实测代价很具体：每次点展开都会重新发一次 `/api/tree`，网络往返期间窄条里先空一下再长出内容——一个会被频繁按的开关不该带一次请求。改成 `hidden={collapsed}` 后，`display:none` 仍然让树离开无障碍树与 Tab 顺序，而 React 不卸载它，展开是瞬时的。实测全程只发一次 `/api/tree`。代价写在明处：**收着也会取一次树**，因为 `useTree` 在 Sidebar 里、不随收起开关；个人规模下这次请求本来就要发（进页面时树是给用户随时展开用的），换来的是展开不闪。

**收起时不渲染「显示已归档」开关，但它的状态不动。** 开关的值一直由 `BoardPage` 持有（D36），收起只是把控件藏起来，展开回来还是原值。没有把它做成「收起时也保留一个图标态」——那要给一个只有 44px 宽的地方塞第二种语义，收益不明显。

**收起时把焦点交给收起按钮。** 追踪：键盘用户在树里选中过某个节点（焦点在树里），点收起后树变成 `display:none`，浏览器把焦点退回 `body`；下一次 Tab 从页面开头重新开始，用户会以为「界面把我扔回去了」。所以收起的那一次 `toggleRef.current?.focus()`。

**这里踩过一个坑，写下来免得再犯**：第一版写成 `useEffect(() => { if (collapsed) focus() }, [collapsed])`，注释还写着「只跑在 collapsed 真正变化之后，首屏不会抢焦点」。这是错的——依赖数组的 effect 挂载时必跑，本地偏好是「收起」时首屏一加载焦点就被拉到按钮上，用户按第一次 Tab 会**跳过整个顶栏**（DOM 里在 `aside` 之前的搜索框与主题控件）直接落到看板里。审阅在 jsdom 与真实 Chrome 里都复现到了。修法是用一个 ref 记住上一次的值，只认 false → true 这一跳（`wasCollapsed` 初值取当前值，挂载那次自然不触发），并给这条路径补了单测（在入口同款的 `StrictMode` 下断言 `document.activeElement` 仍是 `body`）。

**过渡期间要把面板裁住。** 展开的那 150ms 里盒子还是 44px 宽，而展开态的 header 与树已经渲染出来了：「显示已归档」是 `whitespace-nowrap`、树容器 `overflow-y-auto` 会把横向也算成 auto，于是文字被逐字换行、多出来的内容与 15px 横向滚动条会画到看板列上（审阅把过渡放慢到 4s 后逐帧量到：首帧 `aside` 宽 44 而内容宽 99，约 2–3 帧可见）。修法是给 `aside` 加 `overflow-hidden`——最省，且按钮距面板边缘 11px，聚焦环不会被剪。没有顺手给标题加 `whitespace-nowrap`：那会把标题的 min-content 变宽，反而把 22px 的按钮挤出窄条。

**无障碍细节**：按钮带 `aria-controls` 指向被控制的树容器（id 由 `useId` 生成，避免将来页面里出现第二个 Sidebar 时撞 id）；`aside` 的名字固定为「文件树」，**不**随状态变——状态已经由按钮的 `aria-expanded` 表达，可访问名字保持稳定是惯例。收起时顶栏之外只剩 `complementary:文件树`、`heading:文件树`、`button:展开文件树` 三个节点（审阅在真实 Chrome 的 AX 树里核过）。

**偏好仍然只存前端**：`kanban.tree.panelCollapsed` 存单个 boolean（`TREE_COLLAPSED_KEY`），坏值（不是 boolean）按展开算，与 `showArchived` 同一套兜底，且写盘 effect 会立刻把坏值覆盖成 `false`，localStorage 里不会留垃圾。`docs/spec.md` 已经写了「展开折叠状态只存在前端本地存储，不落库」，所以这一步后端一行没动，接口与数据模型都不用改。

**已知限制**：

## D47 看板列撑满看板区，列尾那片空白才是可落点（2026-09-23，用户拍板）

**问题**：用户拖卡片时发现「拖到本列末尾」几乎用不了。追踪：列的实际高度只等于内容高度——实测三列都是 114px，而滚动容器 `main` 是 575px。拖拽落点用 `document.elementFromPoint` + `closest('[data-column-id]')` 命中列（`hooks/useCardDrag.ts` 的 `resolveDropSlot`），所以**最后一张卡片下面的空白根本不属于任何一列**：拖进空列只能落在列头那一条（列头加内容约 114px），列尾插入线也几乎没有可落的位置。

**根因**：`BoardView.tsx` 的看板网格是 `grid min-w-[780px] grid-cols-3 items-start gap-3.5 px-4 pb-7`，网格自身高度只有内容高（实测 142px）。`items-start` 管的是列自身在行内的对齐，**不会把网格撑高**，于是 `Column` 上那句「self-stretch 让列体撑满网格行高」没有可撑的高度。这段注释从第 9 步（`67c1460`）就写着这个意图，一直没生效。

**原型选型**：按前端规则先做了三版可点原型（真机令牌、可切深浅、可真的拖一张卡片看插入线）：

- A 列撑满看板区，列尾空白直接成为落点，不加入任何提示元素；
- B 列仍然内容高，但列体整块可命中，末尾常驻一条虚线「拖到这里放到本列末尾」；
- C 列撑满，只在悬停这一列时显出列尾提示。

用户选 **A**。理由是最小改动、界面不加东西；B 的常驻虚线在空列上很吵。

**改法**：网格的 `items-start` 换成 `h-full`（`height:100%`，网格恒等于 `main` 的高度），`Column` 的 `self-stretch` 不动；底部那 28px 留白 `pb-7` 从网格挪到列上（原因见下面审阅那条）。

**关于 `min-h-full`（第一版这里写过一句错的结论，已更正）**：第一版说「`min-h-full` 会让列高退回内容高」，这是错的。在同一份真实 DOM 上重测：内容不足一屏时两个写法完全一样（`main=674 / grid=674 / 列=646`）；内容超过一屏时**列高也相同**（都是 1115.2，因为列高本来就由内容决定，不是 `min-h-full` 造成的），真正的差别只在网格盒与 `main.scrollHeight`——`min-h-full` 的网格盒会随内容长高（1143.2），`h-full` 的恒等于看板区（674），差的那 28px 正是网格的底部留白。也就是说两个写法都能修好本缺陷，区别是「溢出时网格盒要不要跟内容一起长」。最后这一层差别用「把 `pb-7` 挪到列上」消掉了：列自带内边距，既不产生死区，溢出时也仍然在最后一张卡片下面留出这 28px。

**验证方式**：单测 440 项（api 143 / web 297，新增 1 项守着布局不变量）+ 两端类型检查 + 生产构建；真实浏览器 10 项验收（构建产物 + 真实 API + 用户库副本，脚本不入库、放在 `.tmp-verify/`，验收完删）：三列等高且撑到看板区底部、**拖到空列底部空白处卡片确实落进该列**、塞满 15 张卡片后 `main.scrollHeight > 可视高`、真的能滚、滚动状态下仍能拖到列尾、清理后各列卡片数回到初始、无未捕获异常。深色下也截了图。

**另外量过的两个边界**（都没问题）：375px 窄屏下网格按 `min-w-[780px]` 出横向滚动条，纵向仍是 `grid = main 的 654px`、列照常撑满；操作失败时 `main` 顶部那条 `sticky` 错误提示是个例外——它和网格是兄弟，网格恒等于 `main` 的高度，所以提示条出现时 `main` 会多出约 43px 的滚动、三列整体下移。这是 `h-full` 的必然结果，权衡后接受：提示条是可关闭的临时状态，列本身仍有 500px 以上的高度可用。真要消掉它，得把 `main` 改成 `flex flex-col` 并让网格 `flex-1`（`SearchResults` 与提示条都会跟着变），属于另一件事。

**布局不变量加了一条替身断言**（`test/boardLayout.test.tsx`）：这个缺陷从第 9 步躺到第 12 步才被发现，因为它**在 jsdom 里完全测不出来**（jsdom 不做布局、也没有 `document.elementFromPoint`）。所以退一步钉住让那条链路成立的两个类：网格必须带「确定高度」类（当前是 `h-full`），列必须带 `self-stretch` 与 `pb-7`，且 `pb-7` 不能回到网格上。说清它的边界：它只能证明这几个类还在，证明不了布局真的对；把 `h-full` 换成 `min-h-full` 它不会红（那也确实满足不变量），但把高度类整条拿掉会被拦住——第 9 步那版正是这种写法。

**验收脚本自身踩到的三个坑（与实现无关，但下次别再踩）**：
1. 直接 `fetch` 建任务后立刻量 DOM——React 不知道数据变了、看板没刷新，`scrollHeight` 根本没变，测出来的是假的。必须整页重载后再量，或者走应用自己的入口。
2. 滚动之后按 DOM 顺序取「第一张卡片」——它已经跑到视口上方（实测 `rect.top=-104`），照它算出的坐标是负的，等于「按住一张看不见的卡片」，拖不起来是必然的。要挑**视口内可见**的那张。
3. 清理用的 `Promise.all(...)` 那次没等到结果（`deleted=0`），残留了 14 个临时任务污染了后续测量；改成按标题前缀搜索再逐个 `await` 删除，并在脚本开头也清一遍，脚本才可重复运行。

**审阅发现（2 条建议，都已采纳）**：
1. **列尾最后 28px 仍是死区**：`pb-7` 原来在网格上，属于父容器的 padding，`elementFromPoint` 命中的是网格而不是列。追踪：拖到 `main` 底部之上 5px（列底之下 28px 内）→ 命中 `div.relative.grid.h-full`、`closest('[data-column-id]')` 为 null、插入线消失、松手不生效。反方向也有一条：内容超过一屏时，原来那 28px 是最后一张卡片下面的留白，`h-full` 把它吃掉了（`main.scrollHeight` 从 1143 变 1115）。修法就是把它挪到列上，两条一起解决。
2. **`min-h-full` 的对比结论写错了**（就是上面更正过的那个说法），已改，提交信息里那句也一并改掉。
3. 顺带一条仓库卫生问题：提交时用 `git add -A`，把审阅者放在 worktree 里的 `.tmp-review/kanban.db*` 一起提交了。已从提交里剔除，并给 `.gitignore` 加上 `.tmp-*/`，避免同类事故再发生。

## D48 第 13 步：依赖写入与关键路径计算（2026-09-23）

**问题**：第三批是「任务依赖（DAG）」与「关键路径计算与可视化」，`task_deps` 表从第 1 步就建好了、删除接口也一直负责清理它（D25），但至今没有任何接口写过一条依赖。这一步做后端：`PUT /api/tasks/:id/deps` 与关键路径读取。界面与可视化留给后续步骤——前端规则要求先出原型让用户选，而可视化的布局选型还没定。

**写入端 `PUT /api/tasks/:id/deps`**

- 入参 `{ predecessorIds: string[] }`，整体替换。空数组表示清空——「没有前置依赖」与「没传这个字段」是两件事，所以不给默认值。
- 校验顺序（测试钉死）：schema 形状（数组、非空串、无重复项、无未知字段）→ 任务存在 404 → 任务未归档 400 → 依赖自己 409 → 逐个前置任务（不存在 404 → 不同 `parentId` 400 → 已归档 400）→ 成环 409。
  - 重复项属于入参本身的形状，放在 schema 里，所以它先于「任务存在」；`PATCH` 那条「先资源后入参」的顺序（D23）不适用于它。这条差异写在这里，免得下次被当成 bug。
  - 「先资源后入参」的其余部分与两条 `PATCH` 一致：任务不存在优先于前置任务不存在。
- 环判定：新增 `p → task` 会成环，当且仅当顺着 successor 方向从 task 已经能走到 p（即 p 直接或间接依赖 task）。用一条递归 CTE（`UNION`，脏数据成环也能终止）取可达集合，再按请求顺序找第一个命中项，报错文案带上它是哪一个。
  - 环判定复用的就是同一张图：**当这个任务已经处在某个环的上游时，写入会被拒**（脏数据响亮失败，同 D17）；与这个任务无关的环不影响它。没有额外写一段「先检测全库有没有环」的代码。
- 依赖集合没变时一行都不写：重复提交同一份依赖不刷新 `updated_at`（与 D24 的归档幂等同一个口径）。真的变了才 `DELETE` + `INSERT` + 刷 `updated_at`——依赖变了排期就变了，而 `updated_at` 是「最近改动」的唯一依据（搜索按它排序）。
- 响应 `{ task, predecessorIds }`，`predecessorIds` 按 id 升序。依赖在库里是一个集合（主键是两端），没有顺序，升序只是让响应稳定；前端按 D35 静默重取整张图，不消费这个列表。
- `PUT` 也纳入 `routes/tasks.ts` 的 Content-Type 中间件。原先只拦 `POST`/`PATCH`，漏掉 `PUT` 会让 `curl -X PUT -d`（默认 form-urlencoded）收到「predecessorIds: 不能为空」这种误导文案——zValidator 在 Content-Type 不匹配时直接跳过解析。
- 同层判断只看 `parentId`，与 `columnId` 无关：任务在同一层但分属不同列，依赖完全合法。
- 已知缺口（这一步不做）：归档一个被别人依赖的任务不会清理依赖记录，于是关着「显示已归档」时那些边看不见，打开开关才看得到完整的图。删除路径不受影响（D25 已经清依赖）。要根治得先决定产品口径——「归档时把依赖一起清掉」还是「禁止归档被依赖的任务」——以及被清掉的那一端要不要恢复。

**读取端 `GET /api/board/cpm` 与 `GET /api/board/:parentId/cpm`**

- 根看板没有 `parentId`，所以给它一条独立路径 `/api/board/cpm`，与 `/api/board`（根看板）对称，而不是给 `/api/board/:parentId/cpm` 编一个特殊 id（例如 `root`）。它注册在 `/api/board/:parentId` 之前，并由测试钉住「`/api/board/cpm` 拿到的是图、`/api/board` 与 `/api/board/:parentId` 都还照常」。spec 原先只有 `GET /api/board/:parentId/cpm` 一行，用户验收时授权后已把根看板这一条与两个响应形状（`PUT deps` 的 `{ task, predecessorIds }`、cpm 的 `{ parentId, projectDuration, nodes, edges }`）补进 `docs/spec.md`。
- 响应 `{ parentId, projectDuration, nodes, edges }`。`nodes` 是任务字段（`id`、`title`、`columnId`、`durationMinutes`、`archivedAt`）加上 `earliestStart`、`earliestFinish`、`latestStart`、`latestFinish`、`slack`、`critical`；`edges` 是 `{ predecessorId, successorId, critical }`。节点顺序跟着看板走（列 `orders` + 列内 `orders`），前端不用再排一次。
- 工期原值保留：`null` 表示未估，CPM 按 0 参与计算，界面自己提示未估（spec 的「关键路径」一节要求明确提示）。把 null 在这个接口里改写成 0 会让「未估」在界面上不可分辨。
- **关键边不能只判「两端都关键」**。一个关键任务可能有多个后继，其中一条边并不是让它成为关键的那条：它的最早完成时间早于后继的最早开始时间，迟一点开始也不影响后继。判定是「两端都关键 + 前置的最早完成 == 后继的最早开始」。两个方向的反例（关键节点之间的非紧边、紧边但后继不关键）都写进了 `cpm.test.ts`。
- 成环（只可能来自手工改库）让计算抛 `DependencyCycleError` → 500 并记日志，不返回一张假图（同 D17 的处理哲学）。
- 「显示已归档」沿用统一开关：关着时归档节点与连着它的边都不出现；打开时一起返回。跨层的脏边直接丢掉（两端不都在这一层的边），而不是给前端一条端点不存在的边。
- 空层返回 `projectDuration: 0` 与空数组，不特判。

**纯计算与 SQL 的分工**：`domain/cpm.ts` 只吃 `{ id, durationMinutes }` 与边，不碰数据库；`repositories/deps.ts` 负责取数、拼装与事务。这样 CPM 的数学可以脱离 SQLite 单独测，也能用独立公式交叉验证（见下）。

**验证方式**：单测 479 项（api 182 / web 297，API 新增 39 项）+ 两端类型检查 + 生产构建。CPM 的数学除单例外，还用一份**独立公式**（`ES` = 从任一起点的最长路径、`LF` = 总工期 − 该任务之后的最长剩余路径）在随机 DAG（含未估工期、0 工期、多起点多终点）上逐节点比对，全部一致；真实进程 + 真实 HTTP 也走了一遍六条路径（含 `/api/board/cpm` 不被 `/api/board/:parentId` 抢走、环 409、`PUT` 的 Content-Type）。交叉验证脚本是临时的，跑完即删。

## D49 第 14 步：依赖编辑进任务详情抽屉，按原型 A 做常驻候选列表（2026-09-23，用户拍板）

**问题**：第三批只剩前端。第 13 步（D48）做完了 `PUT /api/tasks/:id/deps` 与 `GET /api/board[/:parentId]/cpm`，但界面上没有任何地方能建依赖——`apps/web` 里连一条 deps 请求都没有，抽屉只改标题、描述、工期。没有编辑入口，图就是一张空图。

**先与用户定的两件事**

- 本步只做**依赖编辑入口**，依赖图（含卡片上的关键路径标记）留到第 15 步单开一个视图。用户中途问「有了图，抽屉编辑是否还有必要」，结论是必要：图上连线要处理吸附、方向校验、成环反馈与撤销，键盘路径还要另配一套「选起点→选终点」的模式；抽屉里的一次勾选是同一件事的最低成本入口，而且能在**点之前**禁用会成环的候选，不必等松手收一个 409。顺序上还有一条硬理由：图先做就没有数据可画，验收只能靠 curl 造。
- 依赖的建立方式是「抽屉里勾选前置任务」，不是图上连线。

**原型选型（按前端规则先出三版可点原型，真机令牌、可切深浅）**：A 常驻复选列表；B 摘要 chips + 弹层选择器；C 前置与后继双视图。用户选 **A**。

- A 的形状：候选常驻展开（最多 260px 滚动），按列分组、已选行高亮（`accent-weak` 底 + 左侧 2px `accent` 竖条），「会形成环」「已归档」两类不可选项在行内写明原因。
- 没选 B：浮层会盖住它正在编辑的 chips，且要多一层「Esc 只收面板、点外面丢弃草稿」的状态机。没选 C：固定 360px 里塞 chips + 候选列表 + 只读后继太长，而且后继那半与第 15 步的图重复。
- 原型里那条「候选超过 8 条才显示过滤框」被采纳（`FILTER_THRESHOLD`）：两三条任务时多一个空控件只是噪音，阈值不是性能考虑。

**不新增后端接口**：要判断「谁能加入而不成环」，需要的是**整层**的边，不是单条任务的列表，所以直接复用第 13 步的 `GET /api/board[/:parentId]/cpm`。新增一个 `GET /api/tasks/:id/deps` 只能回答「现在依赖谁」，省不下成环判断那一次读，反而多一个接口要维护。

**固定 `includeArchived=true` 取图，与看板的「显示已归档」开关解耦**。追踪：任务 T 的前置 A 已归档，用户关着开关打开 T 的抽屉。若图跟着开关走，归档节点与连着它的边都不返回，前端看到的「当前前置」是空集。此时只改标题点保存不会出事（集合没变、不发 PUT），但用户只要**动过一次依赖**（比如加一个新前置），草稿里就不含 A，PUT 是整体替换 → A 那条边被静默删掉，界面上没有任何提示；后端也帮不上忙，请求里根本没有 A。取全图后前端总能看见这条失效依赖，于是能做两件明确的事：提示「有 N 个前置任务已归档，保存后这条依赖会被解除」，并且只要存在这种前置，这次保存就一定发 PUT 把它清掉。代价是多回归档任务的那几行，个人规模可忽略；这个口径顺手补掉了 D48 记下的那条已知缺口的产品侧一半——清理由用户的一次显式保存触发，而不是静默。

**候选与禁用**：候选是这一层的全部任务（含归档），排除自己；列名从看板列查，列名缺失时退化成 `columnId` 而不是丢掉整组。两类禁用原因写在行内，并通过 `aria-describedby` 挂到复选框上（读屏念成「标题，不能选，原因」）：

- 「会形成环：它已经依赖本任务」——判据是「顺着 successor 方向从本任务能走到它」，与后端 `findDependencyCycle` 同源；闭包用显式栈 + `seen`，脏数据成环也不会爆栈。前端自己算，是为了让人点不下去，而不是等松手后收一个 409。
- 「已归档」——后端对含已归档前置的提交整份返回 400，所以这些行不可选；它们仍然显示，好让「图上为什么少了一条边」有解释。

**草稿与两次写**：依赖是抽屉草稿的一部分，与标题、描述、工期共用底部那个「保存」，取消 / Esc / 点遮罩一律丢弃——没有为依赖单独发明「勾了就立即写」，那会让同一个抽屉里出现两种保存语义。保存顺序：先 PATCH 字段，成功后再 PUT 依赖；PUT 只在集合真的变了、或存在已归档前置时才发（后端对同一份集合本来也是幂等空操作，两边口径一致）。PATCH 成功而 PUT 失败时，文案必须说清是哪一半：「标题、描述、工期已保存；依赖未保存：<后端文案>」——否则用户会以为什么都没存上、再点一次，而标题其实已经改了；依赖草稿这时特意留着，改完可以直接重试。

**图没读到时绝不写依赖**：`loading` / `failed` 两种状态下依赖区块只显示状态与重试，`depsNeedSave` 恒为 false。理由是这条：一份「没读到服务端前置」的空草稿如果被当成用户意图提交，就是一次**清空**。所以草稿不用 `useState` 的初始值去猜服务端（图没到位时它会是 `[]`），而是「草稿为 null 时跟着服务端集合走」，用户第一次勾选才产生草稿。

**图的生命周期**：`BoardPage` 进页面就取一次，不是打开抽屉才取；取图固定含归档，并跟着 `refreshAll` 在每次写操作后重取（工期、归档、增删任务都会改变关键路径）。这与 D46 里「收起的树也照样取一次」是同一个取舍：一次 GET 换掉「哪些状态还没准备好」的一整类判断，而第 15 步的图上标记本来就要用它。

**没有做的**：卡片上的依赖数/关键标记、依赖图本身、图上的连线编辑（都在第 15 步）。`docs/spec.md` 的「依赖图可视化」一节要求的关键路径与最早/最晚开始标注也留给第 15 步。

**已知代价（写下来，不在这一步处理）**：一次带依赖改动的保存是两次写（PATCH 字段 + PUT 依赖），而 `useTaskActions` 每次写成功都会 `refreshAll`，于是这一轮保存会把看板、面包屑、依赖图、文件树各取两遍（8 个 GET；改动前一次保存是 3 个）。单用户、本地 SQLite、每层数据量很小的前提下先接受。真要收敛，正确的位置是让 `refreshAll` 合并同一轮里的多次请求，或者让「一次保存」的两次写共用一次刷新——两者都是跨功能的行为改动，不在这一步做。

**验证方式**：单测 531 项（api 182 / web 349）+ 两端类型检查 + 生产构建（顺带确认 `accent-accent`、`border-accent` 这类经 `cx()` 拼出来的类没有被 Tailwind 扫漏，构建产物里能查到 `accent-color:var(--color-accent)`）。真实浏览器 25 项验收（真实 Vite dev server + 真实后端进程 + 用户库副本，脚本不入库、放在 `.tmp-verify/`，验收完删）：现造一个父任务 + 10 个子任务的确定性测试层，覆盖候选分组与计数、成环候选禁用与原因、勾选保存后真的落库、重载后仍勾选、过滤只收敛显示不改集合、取消勾选后边被删、Esc 关抽屉不提交草稿、已归档前置的提示与保存后解除、**草稿里的前置被归档后保存仍然成功且把它解除**（审阅那条阻断的回归）、深色渲染、375px 下抽屉不横向溢出、无未捕获异常。

**审阅发现（1 条阻断 + 4 条建议，都已处理）**

- **阻断项：草稿建立之后某一项变成不可选，保存就永远失败。** 追踪：打开 b 的抽屉（b 的前置是 a）→ 把 a 取消再勾上（草稿就此固定为 `['a']`，不再跟着服务端走）→ Tab 绕回看板、从卡片菜单归档 a（`App.tsx` 里「只在归档的正是被编辑任务时才收抽屉」那条判断让抽屉留着）→ 图重取后 a 成了「已归档」的禁用行，草稿里却还有它。界面上这一行是「已勾选 + 点不动」，「已选 1 项」也算着它，PUT 发出去带 a → 后端 400 `前置任务已归档: a`，文案还写着「字段已保存；依赖未保存」，此后每次保存都重复失败，而用户在抽屉里没有任何办法去掉它。修法是提交前按禁用原因过滤草稿（`savableDeps`）：「已选 N 项」、候选高亮、PUT 内容与 `depsNeedSave` 全部用过滤后的集合。归档那条正好落进「保存时解除失效依赖」的既有语义；成环那条同理（只有草稿建立后关系又被别人改动才会出现）。

## D50 第 15 步：依赖图按原型 A 做成主区整页视图（2026-09-23，用户拍板）

**问题**：第三批只剩可视化。第 13 步给了 `GET /api/board[/:parentId]/cpm`（任务 + 边 + 每个任务的 `earliestStart/latestStart/slack/critical`），第 14 步给了抽屉里的依赖编辑，但界面上没有任何地方把这张图**画出来**——`slack` 与 `critical` 在前端一个字节都没用过。规范的要求是「在同一层的看板上以有向图展示任务与依赖，关键路径上的节点和边用强调色区分；每个任务标注最早开始、最晚开始、松弛时间」，并明确「布局库在实现该批次时选定，不在规范中锁定」。

**原型选型**：按前端规则先做了三版可点原型（单文件 HTML、真实令牌、可切深浅，同一份数据：7 个任务、6 条依赖、关键路径 3 个任务），差别在图的形态：

- A 主区整块换成一张自左向右分层的 DAG，每个节点直接带工期/最早开始/最晚开始/松弛，可平移与适应窗口；
- B 纵向流程图 + 右侧「松弛时间」表（按松弛升序），图与表双向联动；
- C 不离开看板，在三列卡片之间原地画连线。

用户选 **A**。没选 B 的理由：数字全搬进表里，看一个任务要横着对两处；没选 C 的理由：卡片位置由「列 + 列内顺序」决定、与依赖深度无关，实测那一层 6 条边里有 4 条要反向画（如 调研第三方登录 在「完成」、它的后继 实现新登录接口 在「进行中」），连线会穿过卡片、可信度低。

**视图位置与切换**：主区顶部加一行工具栏（`components/ViewToolbar.tsx`），左边是「看板 / 依赖图」分段控件，右边留给当前视图自己的控件（依赖图放图例与缩放，看板为空）。没放进顶栏：顶栏已经有面包屑、搜索框、主题控件，375px 下再塞一个会把主题控件顶出视口（D45 记过）。**搜索态不显示这条工具栏**——结果页占满主区，清空关键词就回到原来的视图。视图状态只在内存里、不落盘：它是「这一次在看什么」，不是偏好（与文件树折叠、显示已归档不同）。

**布局不引图布局库**（规范要求在这里定）。`domain/graph.ts` 的 `layoutGraph` 自己做：Kahn 拓扑序算出「最长路径层号」`layer(v) = max(layer(p) + 1)`，层内保持传入顺序。两条理由：

- 传入顺序就是 cpm 响应的节点顺序，后端已按「列 orders + 列内 orders」排好，所以层内天然是看板上的列序与列内序，前端不需要知道列的存在；
- 取**最长**路径而不是最短：只要有一条前置链没走完这个任务就不能开始，用最短路径会把「依赖链还没走完的任务」摆到与它的前置同一层，图上的左右顺序就与「谁先谁后」矛盾（用例 `test/graph.test.ts` 用 a→x、a→b→c→x 钉住了这条）。

代价写清楚：不做交叉最小化（dagre/elkjs 的主要价值就在这里）。个人规模下这一层的任务数是几十个量级，交叉只是不好看，不影响读；真到上百个节点再换库，`layoutGraph` 是纯函数，换掉它不动组件。

**节点高度定死 124px，标题固定占两行**（`NODE_HEIGHT`/`NODE_WIDTH` 同时用于布局计算与节点的内联 style，是唯一真值）。原型是渲染完量真实高度再摆位置；这里不这么做，因为量高度要求布局走两趟渲染，而且 jsdom 里量出来恒为 0，`layoutGraph` 就没法单测了。代价：标题长的节点会截断（`line-clamp-2`），换来的是坐标可预测、可断言。浏览器验收里量过 7 个节点全 124px 且 `scrollHeight <= clientHeight`（内容没被裁掉）。

**时间口径只有一套**：`lib/format.ts` 的 `groupMinutes`（1 天 = 480 分钟 = 8 小时，按 天 → 小时 → 分 拆段只保留非零段）。新增 `formatScheduleMinutes` 专门给时间量用，唯一的区别是 **0 显示「0 分」而不是「瞬时」**：最早开始/松弛是时刻与差值，不是时长，「松弛 瞬时」会被读成「这个任务一眨眼就做完了」。这里踩过一个坑值得记：出原型时我给子代理的示例里写「480 → 8 小时、900 → 15 小时」，与 `groupMinutes` 的实际输出（480 → 1 天、900 → 1 天 7 小时）矛盾，三版原型一度各按各的口径显示。修法是统一以 `lib/format.ts` 为准——同一个 480 分钟在卡片工期、抽屉工期、图上的最早开始必须是同一个字符串，否则用户会以为是两个不同的数。

**关键边的判定用后端给的 `edge.critical`，不在前端重算**。后端那条判定是「两端都关键 + 前置的最早完成 == 后继的最早开始」（D48 记过为什么不能只看两端是否关键），前端重算一遍只会多一处可能不一致的实现。

**归档：图固定带归档取，前端按开关过滤**（`visibleScheduleGraph`）。依赖图的那次请求沿用 D49 的口径固定 `includeArchived=true`（抽屉要靠它认出已归档的前置），所以「显示已归档」开关在图里只能是前端过滤：关着时去掉归档节点与连着它的边。浏览器验收里数过请求数：开关切换不会多发一次 `/cpm`。已归档节点打开后是斜体标题 + 虚框「已归档」标。

## D51 修复「点过卡片之后新建任务，看板不刷新」（2026-09-23，用户报障）

**现象**：点过任意一张卡片之后，在看板里新建任务只在左侧文件树里出现，主区的看板一直停在旧数据上（要切一层看板或刷新页面才看到）。用户报的原话是「不会立即在看板显示，反倒是文件树会立即显示任务」——树与看板是两条不同的刷新路径，这个差异正好把问题圈在了看板这一条上。

**追踪**：`refreshAll`（写操作成功后的统一刷新）里给拖拽让路的那一行是 `if (!pointerActiveRef.current) refreshBoard()`，也就是「指针还按在卡片上」时跳过看板重取。这个标记的写入有两处：`onDragStart` 里按下就置真，以及一条 effect：

```ts
useEffect(() => {
  if (drag.draggingTaskId === null) pointerActiveRef.current = false;
}, [drag.draggingTaskId]);
```

问题在这条 effect 的触发条件上。它只在 `draggingTaskId` 由「非空」变成 `null` 时才会跑；而一次**按下但不拖**的操作（点卡片进子看板、点「⋯」开菜单）从头到尾 `draggingTaskId` 都是 `null`：`stop()` 里的 `setDraggingTaskId(null)` 是同一个值，React 直接跳过重渲染，effect 也就不跑。于是标记永远为真，此后每一次写操作都静默跳过看板重取——文件树、面包屑、依赖图各自走自己的路径，所以只有看板是旧的。旁证：这一步之前的所有用例都是「打开页面直接新建」，没有一条用例在新建之前先按过卡片，所以 573 项全绿也没拦住它。

**修法**（`useCardDrag` 暴露 `pressed` + App 侧把跳过改成推迟）：

- `useCardDrag` 新增 `pressed` 状态：`begin` 被接受时置真，`stop()` 里置假。`stop()` 是三条结束路径的必经之处（`pointerup` / `pointercancel` / 已进入拖拽时的 `Escape`），所以「按下但不拖」也一定会置回假。谁维护这个状态就放在谁那里——原来由调用方自己记、依赖另一个字段的跳变去推，是这次缺陷的根源。（卸载不走 `stop()`，状态随组件销毁，不需要单独清理。）
- App 里 `pointerActiveRef.current = drag.pressed` 每轮渲染赋值，是唯一的写入点。按下处理函数里**不再**额外同步置一次：同一个状态有两个写入点正是这次缺陷的来源；而 React 对 `pointerdown` 这类离散事件会在微任务之前完成本轮 flush，写操作的回包只可能落在后续宏任务里，所以那次「同步防御」在当前实现下不可达（审阅的变异检验 M10 也证实没有用例能钉住它）。
- 让路的语义从「丢掉这次重取」改成「推迟这次重取」：按下期间记 `deferredBoardRefreshRef`，`pressed` 变回假的那一轮 effect 里补一次 `refreshBoard()`。写操作已经落到服务端了，丢掉那次重取就意味着界面永远停在旧数据上——同一个坑其实还有第二个入口（一次写操作的回包正好落在指针按下的窗口里），一起修掉。
- 拖拽**落定**（有效落点）时把推迟标记清掉：落定之后看板必然还会再取一次（成功走 `refreshAll`，失败走 `commitMove` 里的 `board.reload`），补的那次只会与这次移动的 PATCH 并发——GET 若先回，看板先闪回按下之前的顺序，正是「让路」本来要防的那一下。取消与落在列外的分支没有任何后续请求，推迟的那次照旧补。

**为什么不干脆去掉这个「让路」**：拖拽期间后台 GET 回来的是按下之前的顺序，会把正在拖的卡片打回原位（D42 的乐观重排）。让路是对的，错的是「只跳过不补」以及标记的清除条件。

**验证**：单测 581 项（api 182 / web 399，新增 8 项：4 项 App 端到端、4 项 hook 的 `pressed` 契约）。变异检验（审阅者做了一张 15 行的表，这里摘关键的）：回退到基线 5a6932d → 新增用例全红（证明它们确实钉住原缺陷，不是同义反复）；删掉 `stop()` 里的 `setPressed(false)` → 红 4；删掉补刷新的 effect → 红 1；把「推迟」改回「丢弃」→ 红 1；`pressed` 初值改真 → 红 9；右键也置 `pressed` → 红 1；补刷新的 guard 去掉 → 红 1。真实浏览器 7 项验收（真实 Vite + 真实 API + 用户库副本，headless Chrome 派发真实鼠标事件）：点卡片进子看板再返回后新建 → 新卡片立刻出现且确实多发了一次 `/api/board`；把新卡片拖到「进行中」→ DOM 与服务端都落在 `doing`；再点一次卡片后归档另一张 → 看板上立刻消失；无 console error、无未捕获异常。

**审阅（子代理，只读 apps/ 与 docs/，变异检验在 `.tmp-review/` 的副本里做）**：结论是同意「修复正确」，无阻断与中级缺陷，三条低级意见已处理——(1) 落定后的补刷与移动 PATCH 并发可能让卡片闪回一次原位，已在 `onDrop` 的有效落点分支清掉推迟标记；(2) D51 与 App 注释曾把「卸载」算进 `stop()` 的路径、又暗示窗口外松手已被兜住，与实现不符，已按实际改写；(3) `onDragStart` 里那次「同步防御」赋值删掉（React 对离散事件先 flush 再跑微任务，写回包只可能落在后续宏任务，变异检验 M10 也证明它没有用例能钉住），同一个状态因此只剩一个写入点。审阅顺带确认了三件「不是缺陷」：渲染期写 `pointerActiveRef`（幂等、代码库已有同样模式）、`useEffect` 里的 `pressed` guard 冗余但无害、每次按下/松手多一轮渲染只有性能成本。它同时指出「指针在窗口外松开、`pointerup` 完全不派发」这条局限没有任何用例覆盖（jsdom 模拟不了），与修复前一致，见下。

**计时模型**（`apps/api/migrations/003_task_clock.sql`、`apps/api/src/domain/clock.ts`）：

- 新增 `spent_minutes`（已结算的累计用时，分钟）与 `running_since`（当前这一段的开始时刻）。
- 不变式：`running_since IS NOT NULL` ⟺ `column_id = 'doing' AND archived_at IS NULL`。会改到列或归档状态的写入口有五个（新建、移动、改父级、归档、取消归档），每个都调 `settleClock` 维持它；删除不需要（行没了）。**测试直接按这条不变式断言全库**，而不是逐条断言调用点——漏掉一个写入口会留下「永远不计时的任务」或「停不下来的表」，而这两种毛病都不会让别的断言变红。
- 分钟向下取整；时钟回拨与无法解析的时间串都按 0，不倒扣。取整方向前后端一致，否则卡片上的「已用」会比服务端记账多一分钟。
- 取消归档会绕过 `settleClock` 直接改行，所以归档与取消归档两个分支都在改完之后调一次 `settleSubtreeClocks`：归档后 `archived_at` 已非空，在跑的表被结算停掉；取消归档后处在「进行中」的任务重新开始计时，否则它下次被拖出这一列时不会被结算。
- 迁移回填取**迁移执行时刻**（`strftime('%Y-%m-%dT%H:%M:%fZ','now')`，与 JS 的 `toISOString()` 同格式）而不是 `updated_at`。后者只是最后一次改动的时刻，一个放着没动半年的任务会被算成「已用 180 天」，界面上立刻显示「超期 180 天」这种假数字。

**判定放在前端、且只有一份实现**：后端只存事实，`apps/web/src/domain/reminder.ts` 用本地的 now 算档位。理由不是「前端方便」，而是这个判定会随时间的流逝自己变——同一个任务在两次取数之间就会从弱填充走到临近再走到超期，后端再算一份就是两处实现，迟早分叉（与 D50 记的「关键边的判定不在前端重算」同一个理由）。代价是看板与任务树各挂一个 30 秒的 `useNow` tick，而不是在每张卡片里各挂一个。比较用整数乘法（`剩余 × 10 ≤ 工期`）而不是浮点百分比，避免边界上的浮点误差。

**界面按原型 B 的 HTML 实现，而不是按它的说明文字**：B 的说明写「进行中且已估的任务都画条」，但它的 HTML 给「停在待办但已超期」那张卡也画了满格 danger 条——那正是用户在前一轮定的口径（待办也标超期），所以按 HTML 实现。最终口径：已估工期、未归档、不在完成列的任务都画条，宽度 = min(已用 / 工期, 100%)；三档填充 `accent-border`（未到 90%）/ `accent`（临近）/ `danger`（超期），只用已有令牌，不新增颜色；右下角 11px 小字只在临近（「剩 48 分」）与超期（「超 3 小时」）出现。任务树上放不下整条，用 24×3 的小短条，完整文案进 `title` 与可访问名字。

**几处刻意的取舍**：

- **已估工期但一点没做的任务也画一条 0% 的空轨道**。原型没有这个用例，是我照它的规则推出来的（只在「未估 / 完成 / 归档」不画）。好处是拖进「进行中」立刻有视觉反馈；代价是待办里每个已估工期的卡片底部都有一条很淡的轨道。要改成「已用为 0 就不画」只需在 `reminderView` 里加一个条件。
- **已用正好等于工期时不写「超 0 分」**。这个边界很常见（停着的任务正好用完工期），单独给一句「工期已用完」。
- **条的可访问名字是条件给的**：卡片上有可见小字时条只是装饰（`aria-hidden`），没有小字时（未到 90% 那一档）条是这一行唯一说「还剩多久」的地方，给 `role="img"` + `aria-label`；任务树上没有小字，所以永远可读。这与卡片里已有的子任务进度条（纯装饰、`aria-hidden`）是同一套考虑。
- **卡片不能加 `overflow-hidden`**（右上角「⋯」菜单要伸出卡片），所以贴下沿的条自己带 `rounded-b-[4px]` 贴卡片圆角。浏览器验收里专门量过菜单项没有被裁掉。
- `POST /api/tasks` 直接建在「进行中」列的任务立刻开始计时，与拖进去同义。

**没有做的**：应用外提醒（系统通知、邮件）、截止日期字段、卡片与任务树之外的任何提醒入口（顶栏汇总用户没选）、`spent_minutes` 的写入接口（只由服务端维护）、亚分钟精度、以及「只在有任务在计时时才开 tick」这种优化（个人规模下两个 30 秒定时器可忽略）。

## D55 第 18 步：默认只监听本机 + Host/Origin 白名单 + 请求体上限（2026-09-23，用户拍板「默认收回」）

**问题（实测过，不是推测）**：`apps/api/src/index.ts` 原来只给 `serve()` 传了 `port`，`@hono/node-server` 于是执行 `server.listen(port, undefined)`，Node 对 `undefined` 主机名绑 `::`（本机 `bindv6only=0`，IPv4 一并收）；而启动日志写死「API 监听 http://localhost:…」。用户自己的 dev server 当时就在 `*:3003` 上，实测 `curl http://100.65.77.53:3003/api/health`（Tailscale）与 `curl http://10.32.213.214:3003/api/health`（eth0 私网）都返回 200，而 `/api/tree` 一次返回全库、所有写接口都能改数据，全程无凭据。用户拍板：**默认只服务本机，跨设备访问要显式设 `HOST`**。

**改了什么（`apps/api` 三处 + 一个新模块）**：

- `domain/net.ts`（新增，纯函数）：`hostNameOf` 切分 Host 头（去端口、脱 IPv6 方括号）、`isLoopbackHostName`、`isWildcardHost`、`isAllowedHostHeader`、`isAllowedOrigin`。
- `config.ts`：新增 `Config.host`，默认 `DEFAULT_HOST='127.0.0.1'`；`HOST` 为空串直接报错——「设了但没填」与「没设」是两件事，静默回落默认值会让用户以为自己放开了监听。
- `app.ts`：`createApp(db, { host })`。加一个 **Host 白名单中间件**（所有方法、所有路径，放在路由之前）与一个 **写请求的 Origin 校验**；再加 `bodyLimit({ maxSize: 256KB })`（回 `413 {error:'请求体过大'}`）。顺序是先 Host/Origin 再 bodyLimit：前者不读 body，早拒早省事。
- `index.ts`：`hostname: config.host` 显式传给 `serve()`；日志打印**真实监听地址**；`HOST` 不是回环地址时多打一条「无鉴权、同网段可读写」的提醒。

**Host 白名单的三条规则**（顺序即优先级，全在 `isAllowedHostHeader` 里）：回环主机名永远放行；`listenHost` 本身放行（`HOST=192.168.1.5` 时用那个地址访问要能通）；`allowedHosts` 里列出的主机名放行。第三项由启动方填：**本机所有网卡地址**（`os.networkInterfaces()`）+ `HOST_ALLOW` 里用户自己列的名字，所以 `HOST=0.0.0.0` 时手机用 `http://192.168.1.5:3003` 访问直接可用，而攻击者的域名不在枚举结果里、照样被拒。

**为什么不做「通配就一律放行」**（第一版就是这么写的，被审阅推翻）：当时的理由是「通配监听本来就对同网段敞开，Host 校验挡不住什么」——这个理由混淆了两种攻击面。敞开要求攻击者先进入那个网络；DNS rebinding 只要求用户浏览器打开一个网页。用户按 README 的建议设 `HOST=0.0.0.0` 给手机用时，A2 描述的「任意网页读走全库」会重新成立。改成枚举本机地址之后，跨设备访问照旧可用，rebinding 仍然被挡。**用机器名/域名访问**（例如 MagicDNS 名字）需要写进 `HOST_ALLOW`，否则读能通、写会 403（Origin 不在白名单）——这条也写进了 README。

**为什么回环判定用严格正则而不是 `startsWith('127.')`**：`127.0.0.1.evil.com` 这种域名可以被攻击者解析到 `127.0.0.1` 来做 DNS rebinding，`startsWith` 会把它当成回环，Host 校验当场失效。同样地，`hostNameOf` 按「端口必须是数字」严格解析：`127.0.0.1:3003.evil.com`、`127.0.0.1:3999@evil.com` 这类畸形 authority 一律返回空串（拒绝），不能按第一个冒号宽容切分——否则一个畸形请求就能绕过白名单。用例 `net.test.ts` 专门钉了这些字符串。

**Origin 校验只作用于非 GET/HEAD**：跨站读由浏览器的 CORS 拦（开发态 Vite 同源代理不受影响），而 rebinding 那一类读请求已经死在 Host 这一关。允许的情形是：Origin 缺失（curl、同源表单），或 Origin 的主机名落在同一份白名单里。开发态经 Vite 代理（`changeOrigin: true`）的真实组合是 Host `127.0.0.1:3003` + Origin `http://localhost:5173`，靠「回环」这条规则放行；`Origin: null`、`file://`、畸形串一律拒绝。

**为什么在中间件里从 `c.req.url` 取 Host 兜底而不是只用 `c.req.header('host')`**：Hono 的 `app.request('/path')` 不会自动加 Host 头（单测全走这条路），第一版因此让 123 个既有用例全部 403；而 `@hono/node-server` 恰恰是用 Host 头拼出 `request.url` 的（`server.mjs` 里 `new URL(\`${scheme}://${host}${incomingUrl}\`)`），所以 URL 里的主机名可以当兜底。真实 Host 头优先——它与适配器看到的是同一个值；测试里显式传 `Host` 可以覆盖生产走的这条路径（审阅实测 `new Request(url, { headers: { Host } })` 是保留该头的，fetch 的 forbidden-header 过滤只作用于 `fetch()`）。

**改了什么**（`apps/api` 三处 + 根 `package.json` + README）：

- `app.ts`：新增可选 `AppOptions.staticRoot`。传了就在 **API 路由之后**注册三段：补 `Cache-Control` 的中间件、`serveStatic({ root })` 挂在 GET/HEAD、以及 SPA 回退（非 `/api` 前缀的 GET/HEAD 回 `index.html`）；两道静态 handler 都套一层 `isApiPath` 守卫。

- 根 `package.json` 加 `start` 脚本（`pnpm --filter @kanban/api start`）；README 加「生产运行」一节。

**注册顺序是关键**：Hono 按注册顺序执行、返回即止，所以放在 API 路由之后，静态文件不可能盖住**已注册的**接口；`app.use('*')` 的缓存中间件同理只对「没被接口吃掉」的请求生效。但只靠顺序还不够——`/api/*` 里没注册的那些路径会落到静态层上，所以两道静态 handler 都套了 `isApiPath` 守卫，让「接口的 404 一定是 JSON」不依赖「dist 里恰好没有同名文件」这个巧合。具体触发场景：用户往 `apps/web/public/api/` 放任何东西，Vite 都会原样拷进 `dist/api/`，那时 `GET /api/xxx` 就会被静态层响应成那个文件。用例里故意摆了 `dist/api/echo.json`，断言它仍是 `404 {"error":"not found"}`。

**回退里也排除 `/api` 前缀**，否则接口 404 会变成一张 HTML 页面，而规范要求错误统一是 `{error:string}`。判定写成 `path === '/api' || path.startsWith('/api/')`：`/apiary` 不是接口路径，照常回落页面（有用例）。

**缓存分两档，并且必须在 `serveStatic` 之前设**：`/assets/` 前缀（Vite 产物名带内容哈希）给 `public, max-age=31536000, immutable`，其余非 `/api` 路径给 `no-cache`。`index.html` 绝不能缓存：升级后浏览器拿旧 HTML 去请求已经删掉的旧哈希文件，页面白屏、要手动强刷才能恢复。

- **为什么不能写在 `onFound` 里**（第一版就是这么写的，被我自己的实测推翻）：`serveStatic` 是先 `c.body(stream, 200)` 再回调 `onFound`，而 Hono 的 `#newResponse()` 在构造 Response 时把头部复制了一份，之后 `c.header()` 改的是 `#preparedHeaders`，响应上不会出现这个头。用例里对 `/` 与 `/assets/*` 都断言了具体值，写着 `onFound` 就会红。
- **为什么判定用请求路径前缀而不是文件系统路径**：Windows 的 `path.sep` 是 `\`，按路径判断会漏（`docs/intend.md` 里桌面端优先支持 Windows）。
- **为什么中间件要覆盖全部非 `/api` 路径，而不只覆盖回退**：`serveStatic` 自己会把目录路径解析成 `index.html`（`/` 与 `/board/` 都走这条），根本不经过 SPA 回退——只给回退加头会漏掉最需要 `no-cache` 的那一个。第一版正是漏了 `/`。

**绝对路径这条依赖是实测确认的**：`serveStatic` 的类型注释写着 root 相对 cwd、不支持绝对路径，实现却是 `path.join(root, filename)`，绝对 root 可用。这里就传绝对路径（与启动目录无关），并实测了 `cd /tmp && node <worktree>/apps/api/dist/index.js` 之后 `/` 与 `/assets/*` 都是 200；新增用例用的也是临时绝对目录，把这个依赖钉住。改成相对路径反而会把托管绑在启动目录上。

**路径穿越没有自己写校验**，靠 `serveStatic` 内部的 `tryDecodeURI` + 正则（拒绝含 `..`、`\\`、`//` 的路径）。审阅纠正了我最初的归因，值得写清楚每一条规则各自防什么：**POSIX 上 `..` 与 `//` 本来就被 URL 规范化与保留字挡在门外，真正不可替代的是 `\\` 那条——它是 Windows 上的唯一防线**（`path.win32.join(dist, '/..\\secret.txt')` 会跳到上一层，而 `docs/intend.md` 说桌面端优先支持 Windows；这条规则本机没法端到端验证）。

用例的靶子因此摆了三个位置，缺一个断言就是空的：`outerDir/secret.txt`（`..` 真的解出来才读到）、`outerDir/%2fsecret.txt`（`%2f` 不被 `decodeURI` 解码，越过 `..` 后 `path.join` 落到的就是这个字面名）、`dist/..\secret.txt`（POSIX 上的字面文件名、Windows 上的分隔符）。第一版只有一个靶子，审阅指出**删掉 `serveStatic` 的正则后那两条用例照样绿**——它们当时证明的只是「URL 规范化与 `decodeURI` 不产生 `/`」。补了靶子之后我实测：模拟无正则的落点，`path.join` 读到的正是这两个文件，所以现在删正则必红。另外还有一个坑值得记：`/%2e%2e/secret.txt` 这种写法**测不到** `serveStatic` 的防线——URL 规范化阶段就把它变成 `/secret.txt` 了，必须用 `%2f` 让两个点躲过规范化。

**没做的**：不做按 `Accept` 头区分「浏览器导航」与「资源请求」（未知路径一律回页面，拼错的资源路径也会拿到 200 的 HTML，由前端路由画「未找到」）；不做压缩（`precompressed` 没开，Vite 产物没有 `.br`/`.gz` 文件）；不做 ETag/Last-Modified 的条件请求（`serveStatic` 只回 `Content-Length` 与这次的 `Cache-Control`）；不做多进程/反向代理部署的说明。真实浏览器验收只到 curl 这一层：页面能在浏览器里正常渲染与操作要靠用户这次点一遍。
